HyperLogLog只用幾個位元組估計「有幾個不同的」：同一個人來幾次都只算一次，誤差大約 1.04/√m

超商想知道今天有幾位「不同的」會員來店。最直接的做法是把每張會員卡號放進一個集合，但一家店一天上千人，全台幾千家店、還要按小時、按商品分開算，集合會大到放不下。 HyperLogLog（Flajolet 等人，2007）不記卡號，只準備 m = 2p 個小暫存器：每位來客的卡號先雜湊成 32 位元，前 p 個位元決定放第幾格， 剩下的位元開頭有幾個 0 就是線索——就像丟硬幣，連續 k 次反面的機率是 1/2k，看過越長的一串 0，代表大概來過越多不同的人。 每格只留看過的最大值，同一個人再來，雜湊值一模一樣，不會多算。 它跟 Bloom Filter、Count-Min Sketch 一樣是用雜湊壓縮的「草稿」，這次問的是「有幾個不同的」。 下面先一步一步看 A 店的 12 次來店，再一次灌入十萬次來店看誤差有多準，最後把兩家分店的 HLL 合併成聯集。

為什麼開頭的 0 能估計人數？為什麼重複來店不影響？

                
好的雜湊函數會把每個卡號變成「看起來像隨機」的 32 個位元，每個位元是 0 或 1 的機率各一半。開頭至少有 k 個 0 的機率是 1/2k，
                    所以如果有 n 位不同的會員，我們大約會看到最長 log₂ n 個 0：看到 ρ = 10，大概來過 210 ≈ 1000 人。
                    同一個人的卡號雜湊值永遠一樣，再來一次只是把同一個 ρ 再跟同一格比一次，max 不會變——所以 HLL 數的是「不同的」，不是來店次數。

                
只看一個最大值太看運氣（一個人剛好有很長的 0，估計就翻倍）。HLL 用前 p 個位元把來客分成 m 組，每組各記一個最大值，
                    每組大約有 n/m 人，2M[j] 是那組的粗略估計。合起來用調和平均（倒數的平均）：m / Σ2−M[j]，再乘上組數 m 和修正係數 αm，就是 E = αm·m² / Σ2−M[j]。
                    調和平均對特別大的值不敏感，所以比算術平均穩定得多；論文證明標準誤差約 1.04/√m：m = 1024（p = 10）時約 3%，而且跟 n 是幾千還是幾億無關。

                
人很少時很多格還是 0，調和平均會偏高（每格至少算 1）。這時改用 linear counting：把 n 個人丟進 m 格，某格一直沒人的機率約 e−n/m，
                    空格數 V ≈ m·e−n/m，反推 n ≈ m·ln(m/V)。論文規定 E ≤ 2.5m 而且有空格時用它；E 大到接近 232/30 時雜湊值開始互撞，再做一次大範圍修正。

            

            

                
合併、跟前面方法比較，以及跟實驗室研究的關係

                
    
                    
  • 可以合併：兩個 HLL（同樣的 p、同樣的雜湊）每格取最大值，結果跟把兩邊的資料一起丟進去完全一樣，所以各分店、各台機器、各個小時可以各記各的，最後再合起來估聯集。交集可以用 |A| + |B| − |A ∪ B| 粗估，但誤差會放大。
    • 
                    
  • 記憶體：每格最大值不超過 33 − p，5 個位元就夠，m = 1024 格才 640 個位元組；精確的集合要記住每一張卡號，人越多越大。代價是只能回答「大約幾個」，不能回答「某某人來過沒」（那是 Bloom Filter 的工作），也不能刪除。
    • 
                    
  • 跟前面方法比較：Count-Min Sketch 估每個東西出現幾次，Lossy Counting／Space-Saving 找出熱門的，HLL 估有幾個不同的；三者都是單趟掃串流、記憶體固定，都用雜湊或計數換掉「全部記下來」。
    • 
                    
  • 實際用在哪：Redis 的 PFCOUNT、Google BigQuery 的 APPROX_COUNT_DISTINCT、Presto／Spark 的 approx_distinct，都是 HLL 或它的改良版 HyperLogLog++（64 位元雜湊、小範圍用查表修正偏差）。
    • 
                    
  • 跟實驗室的關係：串流探勘常要知道「這個視窗裡有幾種不同商品／幾位不同顧客」來決定門檻或配置記憶體；增量資料庫也能每批各存一個 HLL，合併後就得到全部資料的不同數，不用重掃。
