I. 牌組模型：四維屬性的笛卡兒積

SET 這副牌的美感來自它的數學結構：每張牌是四個屬性各取三個值的一種組合，不多也不少：

屬性 值域 程式碼中的表示
數量 1 / 2 / 3 count: number
顏色 紅 / 綠 / 紫 'red' | 'green' | 'purple'
形狀 橢圓 / 菱形 / 波浪 'oval' | 'diamond' | 'squiggle'
紋路 實心 / 條紋 / 空心 'solid' | 'striped' | 'empty'
$$ |D| = 3 \times 3 \times 3 \times 3 = 3^4 = 81 $$

所以建牌組就是一個四層巢狀迴圈，沒有任何硬編碼的牌表：

buildDeck.js
function buildDeck() {
    const deck = [];
    for (let count = 1; count <= 3; count++)
        for (const color of COLORS)
            for (const shape of SHAPES)
                for (const shading of SHADINGS)
                    deck.push({ count, color, shape, shading, uid: uidCounter++ });
    return deck;
}

uid 一個欄位，三種用途

牌物件裡那個看似平凡的遞增整數 uid，其實同時承擔了三個角色：

  • DOM 與資料的橋樑：卡片元素上寫 data-uid，之後所有查詢都靠 [data-uid="..."] 選擇器。
  • 選取集合的身分憑證：selected 陣列存的是 uid 而不是索引。這一點很關鍵 —— 檯面會因為補牌與縮編而重排，如果存索引，重排後選取就會指向錯誤的牌。
  • SVG pattern 的命名空間：條紋紋路需要一個 <pattern id>，這裡用 pat-{uid}-{index} 保證唯一。（這件事後來出了問題，詳見「工程反省」。）
一個容易誤判的細節

uidCounter 定義在 IIFE 頂層，而且 newGame() 不會重置它。所以第二局的 uid 是 81–161、第三局 162–242。唯一性依然成立，但任何「uid 應該落在 0–80」的假設在重開一局後就不成立了。

II. 用 Set.size 一次回答兩個問題

SET 的規則是：三張牌在每一個屬性上都必須「三者全同」或「三者全不同」。單屬性的判定只有五行：

checkAttrMatch.js
function checkAttrMatch(v1, v2, v3) {
    const s = new Set([v1, v2, v3]);
    if (s.size === 1) return { valid: true,  type: '全同' };
    if (s.size === 3) return { valid: true,  type: '全不同' };
    return                     { valid: false, type: '不合' };
}

這段程式碼之所以成立，關鍵在於值域大小恰好等於取樣數（都是 3）。在這個前提下，去重後的集合大小只有三種可能，而且各自對應唯一的語意：

Set.size 意義 合法？
1 三者相同 ✅ 全同
2 恰好兩張相同、一張不同 ❌ 唯一的非法型態
3 三者互異（必然覆蓋整個值域） ✅ 全不同

注意 size === 3 那行的推論：因為值域只有三個值，三個互不相同的值必然剛好用掉全部三種 —— 所以「互異」自動等於「全不同」，不需要額外檢查。一次 Set 建構就同時回答了「合法嗎」與「是全同還是全不同」兩個問題，而後者正好是 UI 要顯示的判定說明。

判定與解釋一次算完

evaluateTrio() 回傳的不只是布林值，還帶一個 breakdown 物件記錄四個屬性各自是「全同」還是「全不同」。這個物件後來被三個地方共用：解答面板的屬性標籤、SET 類型統計、遊戲結束總結。UI 完全不需要重算「哪個屬性全同」—— 這是把衍生資訊在來源處一次算好、往下傳遞的典型好處。

III. 有限體視角：任兩張牌唯一決定第三張

把每個屬性值映射到 $\{0, 1, 2\}$，一張牌就是有限體 $\mathbb{F}_3$ 上的四維向量。此時「全同或全不同」有一個極漂亮的等價敘述：

$$ \{a, b, c\} \text{ 是 SET} \iff a + b + c \equiv \mathbf{0} \pmod 3 $$

（這裡的加法是逐分量進行的，四個屬性各自獨立取模。）驗證很簡單：若三者相同，$3a \equiv 0$；若三者互異則是 $0+1+2 = 3 \equiv 0$；而「兩同一異」會得到 $2a + b$，在 $a \ne b$ 時必不為 0。

屬性值編碼：紅=0  綠=1  紫=2

  全同   0 + 0 + 0 = 0  ≡ 0  ✅
  全同   2 + 2 + 2 = 6  ≡ 0  ✅
  全不同 0 + 1 + 2 = 3  ≡ 0  ✅
  兩同一異 1 + 1 + 0 = 2 ≢ 0  ❌
  兩同一異 2 + 2 + 1 = 5 ≡ 2  ❌
$\mathbb{F}_3$ 上的加法就是 SET 規則本身

這個觀點帶來一個直接的推論：任意兩張不同的牌，唯一決定第三張。因為 $c \equiv -(a+b)$ 只有一個解。於是全牌組的 SET 總數可以直接算出來：

$$ \frac{\binom{81}{2}}{\binom{3}{2}} = \frac{81 \times 80 / 2}{3} = \frac{3240}{3} = 1080 $$

（每組 SET 含三個「兩張牌的配對」，所以要除以 3。）我把遊戲裡的 findAllSetsIn() 直接餵進完整的 81 張牌驗證，得到的答案正是 1,080 —— 實作與理論吻合。

為什麼專案沒有採用這個寫法

$(a+b+c) \bmod 3$ 的版本更短更快，但它需要先把字串屬性編碼成數字，而且算不出「哪個屬性是全同」 —— 那正是解答面板要顯示的資訊。現行的 Set.size 版本雖然理論上笨一點，卻同時產出了可讀性與 UI 需要的中文標籤。在這個規模下（每局最多 1,330 次判定），可讀性勝過微優化。

IV. 全解搜尋的複雜度與可行的優化

「提示」功能要列出檯面上所有可能的 SET，實作是最直接的三重迴圈：

findAllSetsIn.js
for (let i = 0;     i < cards.length; i++)
for (let j = i + 1; j < cards.length; j++)
for (let k = j + 1; k < cards.length; k++) {
    const res = evaluateTrio(cards[i], cards[j], cards[k]);
    if (res.isSet) solutions.push({ cards: [...], breakdown: res.breakdown });
}

複雜度是 $\Theta\!\left(\binom{n}{3}\right)$：

檯面張數 n 三元組數 C(n,3) Set 物件配置數（每組 4 個）
12（標準） 220 880
15（補一次牌） 455 1,820
18 816 3,264
21 1,330 5,320

這在 JS 引擎裡是微秒級的工作，完全不需要優化。但如果真要優化，前一節的「兩張決定第三張」性質給了一個 $O(n^2)$ 的做法：

optimized_search.js
// 把每張牌編碼成 0..80 的整數（四位三進位）
const encode = c => c.count - 1 + 3 * (CI[c.color] + 3 * (SI[c.shape] + 3 * DI[c.shading]));

const present = new Map();  // code → card
cards.forEach(c => present.set(encode(c), c));

for (let i = 0; i < n; i++) for (let j = i + 1; j < n; j++) {
    // 逐位計算 -(a+b) mod 3，直接得到唯一的第三張牌
    const third = thirdCode(code[i], code[j]);
    const c3 = present.get(third);
    // 加上索引條件避免同一組被找到三次
    if (c3 && indexOf(c3) > j) solutions.push([cards[i], cards[j], c3]);
}

n = 21 時從 1,330 次三元組判定降到 210 次配對查表。我沒有採用它，因為現行版本在最壞情況也遠低於一幀的預算，而三重迴圈的意圖對讀者一目了然。記錄下來是為了說明「知道有更好的做法，但這裡不需要」。

V. 實測統計：無解機率與類型分布

我把遊戲的 buildDeck / shuffle / findAllSetsIn 原封不動抽出來，做了 20 萬次隨機取樣。這些數字直接解釋了玩家的體感：

12 張 2.782 3.222 % 每 31 副檯面 1 次
15 張 5.756 0.041 % 每 2,439 副檯面 1 次

這組數字解釋了一個設計決策

3.2% 不是可以忽略的機率 —— 玩十局大概就會碰到一次死局。這正是為什麼「提示」按鈕必須兼任無解自動補牌的角色：它不只是給卡關的玩家看答案，而是遊戲能繼續進行的必要機制。補到 15 張之後無解機率驟降到 0.04%，補牌一次幾乎就能解決問題。

15 種 SET 類型，數量呈完美的 2 的次方

依「四個屬性各自是全同還是全不同」分類，理論上有 $2^4 = 16$ 種組合，但四個屬性全同是不可能的（那代表三張完全一樣的牌，而 81 張牌裡沒有重複），所以恰好 15 種。實測 1,080 組 SET 的分布是：

「全同」的屬性個數 k 類型數 每種類型的組數 小計
0（四屬性全不同） 1 216 216
1 4 108 432
2 6 54 324
3 4 27 108
4 0（不可能） — 0

組數服從一個乾淨的公式：

$$ N(k) = 27 \cdot 2^{\,4-k}, \qquad \sum_{k=0}^{3} \binom{4}{k} N(k) = 1080 $$

這也是遊戲結束總結面板的統計基礎：它會列出你這局找到了哪幾種類型、各幾組。四屬性全不同（216 組，佔 20%）是最常見也最難看出來的類型 —— 沒有任何一個屬性可以當作「錨點」來輔助辨識。

VI. SVG 程序化繪圖：三種形狀與條紋紋路

81 張牌沒有用任何圖片素材，全部由字串模板即時生成 SVG。三種形狀各有巧思：

形狀 SVG 元素 為什麼這樣畫
橢圓 <rect rx="36"> 用圓角矩形而非 <ellipse>：rx 幾乎等於半寬，形成膠囊形，更接近實體牌的外觀
菱形 <polygon> 四個頂點，加 stroke-linejoin="round" 避免尖角爆刺
波浪 <path> 四段三次貝茲曲線（C 指令）組成 S 形後 Z 閉合

條紋的關鍵在 patternUnits

striped_pattern.svg
<pattern id="pat-42-0" width="100" height="9"
         patternUnits="userSpaceOnUse">
    <line x1="0" y1="4.5" x2="100" y2="4.5"
          stroke="var(--set-red)" stroke-width="2.5"/>
</pattern>

一格 pattern tile 高 9 單位、正中間一條寬 2.5 的水平線，平鋪後就是等距橫條紋。真正重要的是 patternUnits="userSpaceOnUse"：

預設值 objectBoundingBox

pattern 會依照套用形狀的外框比例被拉伸。菱形、膠囊、波浪的長寬比不同，於是三種形狀的條紋密度會不一致，看起來很廉價。

userSpaceOnUse

pattern 用 viewBox 的使用者座標系，不隨形狀縮放。三種形狀的條紋間距完全相同。

另外，SVG 的 fill 與 stroke 直接吃 CSS 自訂屬性（fill="var(--set-red)"），所以整套配色的唯一真相來源就是 :root —— 想調整紅綠紫的色相，改三行 CSS 就好，不必碰 JavaScript。

VII. 檯面縮編：不用 splice 的四步演算法

這是整個專案裡最有趣的一段邏輯。需求看起來很簡單，但暗藏衝突：

  • 配對成功後，被選走的三張牌要在原位補上新牌（不能讓整個版面位移）
  • 但若之前因為無解而補過牌（檯面 > 12 張），成功配對後應該縮回 12 張，而不是無限膨脹

解法的第一步就決定了一切：挖洞時用 null 佔位，絕不用 splice。這樣陣列長度與其他牌的索引都不變，CSS 上再用一個 .card.empty（透明、pointer-events: none）撐住 grid 格位。之後的四個步驟：

初始：15 張檯面，玩家選走 index 0, 1, 2

 [ 0][ 1][ 2][ 3][ 4]        c0  c1  c2  c3  c4
 [ 5][ 6][ 7][ 8][ 9]   →    c5  c6  c7  c8  c9
 [10][11][12][13][14]        c10 c11 c12 c13 c14

① 挖洞（null 佔位，長度不變）
 [ ✕][ ✕][ ✕][c3][c4]  c5 ... c14

② 從尾端 pop 到剩 12 格，收進 extraCards
 extraCards = [c14, c13, c12]
 board.length = 12

③ 由左往右填洞，優先用 extraCards，用完才抽牌堆
 [c14][c13][c12][c3][c4]  c5 ... c11        ← 淨效果：15 → 12

④ 若 pop 出來的牌比洞還多（檯面 ≥ 18 張），推回尾端
 board.push(...) 剩餘的 extraCards
同一段程式碼同時實現「原位補牌」與「智慧縮編」兩種行為
board_shrink.js
// ① 把被選中的位置挖空（保留長度）
indices.forEach(idx => { board[idx] = null; });

// ② 超過 12 張就從尾端收回來
let extraCards = [];
while (board.length > 12) {
    let c = board.pop();
    if (c !== null) extraCards.push(c);
}

// ③ 填洞：先用尾端搬來的，沒有才抽牌堆
for (let i = 0; i < board.length; i++) {
    if (board[i] === null) {
        if (extraCards.length > 0) board[i] = extraCards.shift();
        else if (deck.length > 0) board[i] = deck.shift();
    }
}

// ④ 檯面 ≥18 張時 pop 出的會比洞多，推回尾端
while (extraCards.length > 0) board.push(extraCards.shift());
一個已知的小瑕疵：牌序被鏡射

步驟 ② 用 pop()（從尾端取）而步驟 ③ 用 shift()（從頭取），兩者方向相反，所以尾端三張牌會以反序落到前面的洞裡。功能完全正確，但視覺上牌的位置跳動不太直覺。加一個 extraCards.reverse() 或改用 board.splice(12) 取尾段即可保序 —— 這是留著沒改的小債。

VIII. 兩個小而有效的 UI 決策

1. 用 outline 而不是 border 畫選取框

卡片有四種狀態框：選取（金）、提示高亮（藍）、正確（綠）、錯誤（紅）。全部用 outline 實作，而 .card 的基礎樣式預先寫好 outline: 3px solid transparent。

原因是 outline 不佔盒模型空間。如果用 border，切換狀態時卡片尺寸會變化，觸發 reflow 讓整個 grid 抖一下；用 outline 則只是重繪，而且因為透明框一開始就存在，連 outline 寬度都不會變。

2. 非阻塞的自製彈窗

原生 alert() 會凍結 JS 執行緒 —— 對這個遊戲是致命的，因為配對的視覺回饋依賴 setTimeout（成功 400ms 綠框、失敗 500ms 紅框）。彈窗一凍結，動畫節奏就亂掉。

自製彈窗用 visibility + opacity 的 transition 實作（用 display 就吃不到過場動畫），並支援 autoCloseMs = 0 表示常駐。更重要的是：改成非阻塞之後，作者乾脆讓「配對成功／失敗」完全不彈窗，只留下綠框紅框，把彈窗保留給「無解補牌」與「遊戲結束」這兩個真正需要告知的時機。

IX. 一個真正的競態 bug：判定重入

這是全站自我審查中找到最嚴重的問題，而且它會實際影響分數與牌面。

觸發條件

配對成功後，程式會先亮綠框，然後 setTimeout(..., 400) 才真正動資料。問題出在點擊處理器在這 400ms 內沒有任何鎖：

the_bug.js
function onCardClick(uid) {
    if (gameOver) return;

    if (selected.includes(uid)) { /* 取消選取 */ return; }
    if (selected.length < 3) { selected.push(uid); syncSelection(); }

    // 🐛 selected 已經是 3 張、但 400ms 的結算還沒跑
    //    此時點第 4 張牌：上面兩個 if 都不成立，卻會掉進這裡
    if (selected.length === 3) {
        checkSelected();          // ← 同一組 SET 被判定第二次
    }
}

後果

  1. recordFoundType() 被呼叫兩次 → 結束總結的類型組數多算。
  2. 排入第二個 400ms timeout，而它捕捉的是舊的 indices。
  3. 第一個 timeout 正常完成挖洞、補牌；第二個 timeout 接著用舊索引把剛補進來的三張新牌再挖掉一次，並且 foundCount++。
  4. 淨結果：分數多加一分、白白吃掉三張牌、牌堆莫名少了三張。
為什麼這種 bug 很難在手動測試中發現

它需要在 400ms 的視窗內完成「第四次點擊」。正常玩的時候，人看到綠框會自然停下來 —— 但手速快的玩家、或連點的玩家一定會踩到。而且症狀是「分數怎麼多了一分」這種模糊的異常，不會拋錯、不會當掉，很容易被當成自己記錯。

修法：一個結算鎖

the_fix.js
let resolving = false;   // 結算動畫進行中

function onCardClick(uid) {
    if (gameOver || resolving) return;   // ← 入口就擋掉
    // ...
}

function checkSelected() {
    if (resolving) return;                  // ← 雙重保險
    resolving = true;

    if (result.isSet) {
        setTimeout(() => {
            /* 挖洞、縮編、補牌、計分 */
            resolving = false;            // ← 動畫結束才解鎖
            checkGameOver();
        }, 400);
    } else {
        setTimeout(() => { /* 清紅框 */ resolving = false; }, 500);
    }
}

鎖必須加在兩個地方：onCardClick 的入口（讓第四次點擊完全無效，連選取狀態都不改）以及 checkSelected 的開頭（防止任何其他呼叫路徑繞過）。newGame() 也要重置它，否則在結算動畫中按「重新開始」會讓遊戲永久鎖死。

驗證方式

用 jsdom 載入實際頁面，連點三張牌觸發判定，接著在動畫期間再點第四張，斷言（1）選取數不變（2）分數不變（3）動畫結束後鎖已釋放、可以繼續操作。這種「時序相關」的 bug 靠人工測試極不可靠，但用程式模擬點擊就非常確定。

X. 另外兩個修掉的問題

1. 重複的 SVG pattern id

條紋 pattern 的 id 是 pat-{uid}-{index}，在檯面內確實唯一。但「提示」面板的解答縮圖會對同一張牌物件再呼叫一次 cardMarkup()，於是產生完全相同的 id —— 文件裡出現重複 id，是無效 HTML。

目前之所以看起來正常，是因為瀏覽器解析 url(#id) 時取文件順序的第一個，而 .board 剛好在 aside 之前，所以縮圖引用到的是檯面卡片的 pattern，顏色與幾何又完全一樣。但這是巧合，不是設計：一旦檯面重繪（boardEl.innerHTML = ''）而面板還在，被引用的 pattern 就消失了，條紋會變透明。

修法是給 shapeSVG() 與 cardMarkup() 加一個 scope 參數，解答面板傳入 `s${index}-`，讓兩邊的 id 命名空間徹底分離。

2. 牌堆剩 1～2 張時補牌會塞進 null

無解自動補牌的原本寫法是連續三次 board.push(deck.length > 0 ? deck.shift() : null)。因為外層只檢查過一次 deck.length === 0，牌堆只剩 1～2 張時，第二、三次 push 會塞進 null，檯面尾端出現不必要的空格。

改成 Math.min(3, deck.length) —— 有幾張就補幾張，並在補完後補呼叫一次 checkGameOver()（因為補完可能仍然無解，而牌堆已經抽乾，那就是遊戲該結束的時刻）。

XI. 誠實的已知限制

  • 靜默死局。checkGameOver() 只在「配對成功後」與「按提示發現無解」時被呼叫。如果牌堆已空、檯面無解，而玩家就是不按提示也不操作，遊戲不會自己宣告結束，計時器會繼續跑。標準 SET 是發牌時就檢查，這裡採用懶惰偵測，換來的是實作簡單。
  • 初始 12 張沒有檢查是否有解。約 3.2% 的機率一開局就無解，玩家必須先按一次提示才會拿到補牌。這是上一點的同源問題。
  • 提示高亮只支援滑鼠。解答項目用 mouseenter / mouseleave 高亮對應卡片，觸控裝置完全觸發不到 —— 而 CSS 又給了 cursor: pointer，形成「看起來可點、實際不可點」的落差。應該補上 click 與 focus 事件。
  • 卡片完全無法用鍵盤操作。卡片是純 <div>，沒有 tabindex、沒有 role、沒有 aria-pressed、也沒有 keydown 處理。SVG 也缺 role="img" 與標題，螢幕閱讀器無法得知「兩個紅色空心菱形」這種資訊。
  • 顏色是規則的一部分，但沒有色盲輔助。紅與綠是 SET 四屬性之一，紅綠色盲玩家難以區分。正確做法是提供一個「顯示屬性文字」的輔助模式，或改用色盲友善的三色調色盤。.correct / .wrong 的回饋也只靠綠框紅框，沒有文字或圖示替代。
  • .solution-panel 的 !important 是順序造成的技術債。兩個 media query 寫在基礎規則之前，同特異度下後者勝出，所以只能靠 !important 壓過去。把 media query 移到檔尾就能拿掉。
