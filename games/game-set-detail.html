I. 81 張牌其實是一個四維空間

SET 的每張牌有四個屬性：數量（1、2、3）、顏色（紅、綠、紫）、形狀（橢圓、菱形、波浪）、紋路（實心、條紋、空心）。每個屬性三選一，四個屬性互相獨立，所以整副牌就是所有組合，不多也不少：

$$ |D| = 3 \times 3 \times 3 \times 3 = 3^4 = 81 $$

程式裡沒有任何寫死的「牌表」，牌組是四層迴圈直接產生的。每張牌另外帶一個遞增的 uid，它同時扮演三個角色：辨識玩家點了哪張牌、在連線時當作「這張牌還在不在檯面上」的依據，以及產生 SVG 條紋圖樣時的唯一名稱。

「三張牌是不是 SET」的規則是：每一個屬性都必須三張全相同，或三張全不同，只要有一個屬性出現「兩張一樣、一張不同」就不算。程式用一個很省事的方法判斷：把三張牌在某個屬性上的值丟進 Set，看裡面剩幾種值——剩 1 種是全相同、剩 3 種是全不同，剩 2 種就不合格。一次就同時回答了「合不合法」和「是哪一種合法」。

為什麼「兩同一異」會成為提示文字

對戰時選錯，畫面會直接告訴你是哪幾個屬性「兩張一樣、一張不同」。這不是另外寫的規則，而是同一個判斷順手留下的副產品：判定時本來就知道每個屬性各剩幾種值，把剩 2 種的屬性名稱列出來就是錯誤原因。

II. 任兩張牌，決定唯一的第三張

如果把每個屬性的三個值當成 0、1、2，「全相同或全不同」剛好等於「三個值加起來是 3 的倍數」。所以每張牌可以看成一個四維向量，三張牌是 SET 的條件就是三個向量相加後每一維都是 0（mod 3）：

$$ a + b + c \equiv \mathbf{0} \pmod 3 \quad\Longleftrightarrow\quad c \equiv -(a+b) \pmod 3 $$

這帶出一個很漂亮的性質：任意兩張牌，都剛好有一張牌能和它們湊成 SET。所以整副牌的 SET 數量可以直接算出來：從 81 張裡挑兩張，每一對對應一張第三張，但每組 SET 會被它的三對各數到一次：

$$ \frac{\binom{81}{2}}{3} = \frac{3240}{3} = 1080 $$

這個性質目前用在統計與說明上；全解搜尋仍然用最直接的「三張三張逐一檢查」，理由放在下一節。

III. 全解搜尋：知道有更快的寫法，但這裡不需要

單人模式的「提示」要列出檯面上所有的 SET，對戰模式的「沒有 SET？補牌」要知道檯面上有沒有解、有幾組。兩者都用同一個函式：把檯面上的牌三張三張全部試過一遍。

211,330實務上幾乎不會到這麼多

利用上一節「兩張決定第三張」的性質，可以改成：每兩張算出需要的第三張，再查它在不在檯面上，檢查次數從 $\binom{n}{3}$ 降到 $\binom{n}{2}$。我沒有採用，因為就算 21 張，現行寫法也遠遠用不到一個畫面更新的時間，而三重迴圈的意圖任何人一看就懂。記在這裡，是為了說明「這是取捨，不是不知道」。

IV. 實測：無解有多常見？

我寫了一個獨立的模擬程式，用跟遊戲一樣的判定規則隨機發牌十萬次，量出下面這些數字（之後每次改動規則都會重跑一次對照）：

情況結果
12 張完全沒有 SET約 3.2%（大約每 30 局開局就會遇到一次）
15 張完全沒有 SET約 0.04%
12 張平均有幾組 SET約 2.8 組

3.2% 不是可以忽略的機率，這個數字直接決定了「無解時怎麼辦」必須是遊戲的一部分，而不是例外處理。單人模式交給「提示」：真的無解就自動補 3 張。對戰模式的做法改過一次，見「問題與修正」的 #8：現在是一顆「沒有 SET？補牌」按鈕，誰都可以按。

15 種 SET 類型

四個屬性各自是「全同」或「全不同」，理論上有 2⁴ = 16 種組合，但「四個屬性全同」代表三張是同一張牌，不可能發生，所以實際上是 15 種。遊戲結束的總結會依照這 15 種類型統計你找到了哪些。

V. 81 張牌沒有任何一張圖片

所有圖案都是即時產生的 SVG：橢圓用圓角很大的矩形畫成膠囊形，菱形是四個頂點的多邊形，波浪是幾段曲線組成的 S 形。條紋則用 SVG 的平鋪圖樣，一條橫線不斷重複。

條紋有一個容易踩的設定：圖樣的座標系統要用 userSpaceOnUse。預設值會依每個形狀的外框比例拉伸圖樣，結果三種形狀的條紋粗細和間距都不一樣，看起來很廉價。改成使用畫布本身的座標後，三種形狀的條紋就完全一致了。

顏色則直接引用 CSS 變數，所以整套紅綠紫的配色只定義在一個地方，網站圖示的三個形狀也是用同樣的顏色畫的。

VI. 拿走三張之後，牌怎麼補？

拿走一組 SET 之後有兩種情況要同時處理：

  1. 檯面是 12 張：被拿走的三個位置，直接從牌堆補三張新牌到原位，其他牌一張都不動，玩家不用重新掃視整個檯面。
  2. 檯面超過 12 張（之前因為無解補過牌）：這時不補新牌，而是把最後面多出來的牌搬到空位，讓檯面縮回 12 張，不會越玩越多。

做法是挖洞時先用空位佔住，不把陣列縮短，這樣其他牌的位置都不會位移；接著依「多餘的牌優先、再從牌堆補」的順序把洞填滿。同一段邏輯同時處理了這兩種情況。

一個留著沒改的小瑕疵

多出來的牌是從尾端一張張取出，再依序填進前面的洞，所以這幾張搬過去時順序會反過來。功能完全正確，只是位置變化不太直覺；要改只需要先把取出的順序反轉一次。

I. 房主說了算

連線的需求很單純：大家打開同一個網頁、輸入暱稱，一個人建立房間拿到四位數字，其他人輸入數字加入（最多 6 人），然後搶同一副牌，誰先送出合法的三張就算誰的。

網站放在 GitHub Pages，沒有後端伺服器，所以整局牌的「真相」放在房主的瀏覽器裡：檯面、牌堆、每個人的分數都以房主為準。房主和每一位加入者之間各有一條連線，加入者之間不直接相連。加入者每次選滿三張，只是送出一個「我要這三張」的請求，由房主驗證：

  • 這三張牌是不是都還在檯面上（可能剛被房主拿走）。
  • 這三張是不是真的構成 SET，房主會自己重算一次，不相信對方傳來的判斷。
  • 請求是不是屬於這一局，避免重新開始之後，上一局遲到的請求被算進新局。

驗證通過，房主就用跟單人模式完全相同的流程挖洞、補牌、加分，再把最新的牌面和名單廣播給所有人。電腦對手也走同一條路，只是由程式在隨機的延遲後送出請求。三種模式共用一套判定與計分，沒有任何一種模式有自己的特例。

「先送達的人得分」代表什麼

比的是誰的請求先抵達房主。房主自己點牌不用經過網路，所以房主有一點天生的優勢，大約就是一趟網路傳輸的時間。直連時通常只有幾十毫秒；走備援通道時大約多 0.1～0.3 秒。對 SET 這種需要找好幾秒的遊戲，這個差距在可以接受的範圍內。

II. 兩條路：先試直連，打不通就走備援

連線分成兩層，對玩家來說是自動的，狀態列只會顯示「（直連）」或「（經由備援伺服器）」：

  1. WebRTC 直連：透過 PeerJS 公開的配對服務交換連線資訊，之後兩台裝置直接傳資料，延遲最低。房間碼就是房主在配對服務上登記的名稱，所以同一個號碼不會被兩個人同時用掉。
  2. MQTT 備援通道：如果 10 秒內直連打不通，就改用公開的 MQTT 訊息伺服器（EMQX，HiveMQ 當第二選擇）轉送。兩邊只要能連上網路就連得到，不需要兩台裝置之間互相打得通。

為了讓對局邏輯不必分辨走的是哪一條路，備援通道被包成跟 PeerJS 連線物件一樣的介面：一樣有開啟、收資料、關閉這幾個事件，一樣用 send() 送資料。上層的搶答、補牌、重新開始完全沒有改。

兩條路都加上了心跳：每 5 秒互傳一次訊號，20 秒沒收到對方任何訊息就判定斷線。直連在對方分頁被直接關掉時，要 30 秒以上才會自己發現，心跳把這個時間縮短，也讓「斷線重連」能更快接手（見第 VI 節）。

備援通道還額外處理了兩件直連本來就有的事：每 4 秒互傳一次心跳，15 秒沒收到對方任何訊息就視為斷線；另外，加入者連上伺服器時會先登記一則「遺囑訊息」，如果分頁被直接關掉，伺服器會代替它通知房主「對方離開了」。

公開伺服器的代價

公開 MQTT 伺服器上的訊息，理論上任何人只要訂閱同一個主題就看得到。這裡傳的只有牌局資料（牌面、分數、誰搶了哪三張），只有自己取的暱稱，沒有其他個人資訊，所以可以接受；如果之後要傳聊天或帳號資料，就不能再用這條路。

III. 從兩人到多人

連線一開始只支援兩個人，程式到處都假設「只有兩個人」：分數只有「房主」和「加入者」兩格、房主只保留一條連線、重新開始只等一個人回覆、提示文字寫的都是「對手」。改成多人時，這些全部要換掉：

雙人版多人版
身分房主／加入者每個人一個玩家代號＋暱稱
計分兩格固定的分數依玩家代號記分，畫面上列出所有人的暱稱、分數與名次
連線房主只接一條房主同時接最多 5 條，每條各自有心跳與斷線判定
開局有人連進來就開始先進等待室，房主看人到齊再按「開始遊戲」；中途加入的人從 0 分開始
重新開始對方同意就開新局所有在線的人都同意才開；任何人拒絕或 20 秒沒到齊就取消，並說出是誰
提示「對手」直接寫暱稱，例如「小明 搶先拿走了同一組 SET」

暱稱存在瀏覽器裡，下次打開自動帶入；長度限制 12 字，並過濾掉換行等控制字元。所有顯示暱稱的地方都以純文字放進畫面，不會被當成網頁語法執行，避免有人取一個「看起來像程式碼」的名字來搗亂。

重新開始為什麼要「全部同意」

多人時有幾種常見做法：多數決、房主說了算、全部同意。多數決會讓少數人的進度被強制作廢；房主說了算對其他人不公平。全部同意最保守，缺點是一個人不回應就卡住，所以加了 20 秒逾時，並明確顯示「誰沒有回應」。人在線上的時候，按一下就能同意，成本很低。

IV. 對戰規則的設計

補牌由玩家決定。對戰時沒有提示，系統也不會偷偷補牌。下方有一顆「沒有 SET？補牌」按鈕，誰都能按：檯面真的無解，就補 3 張，所有人都會看到是誰補的；如果其實還有解，就不補，只告訴大家「還有幾組」，不說是哪幾組。按錯的人別人也會看到，判斷「到底有沒有解」本身就成了搶快的一部分。同一個人按完要等 2 秒才能再按，避免狂按。

別人結算時仍然可以選牌。有人拿走一組 SET 後，那三張會亮約 0.8 秒再換掉。這段時間內，其他人仍然可以選別的牌；選滿三張就先排隊，等更新完立刻判定。好幾個人同時找到不同的 SET，每一組都算分。

遊戲結束時直接「再來一局」。比分視窗會列出所有人的名次（同分同名次），視窗裡就有「再來一局」按鈕，不必先關掉視窗；有人拒絕時會看到「小明不想跟你玩了」。

V. 配對成功的回饋要放在哪裡

多人對戰時，最常見的疑問是「剛剛是誰拿走了哪三張？」原本的綠框只亮 0.4 秒就換牌，根本來不及看。要讓它停久一點，有兩個方向：

做法好處代價
原地停久一點不用找，牌就在原本的位置被拿走的牌一直佔著位置，所有人都要等它們換掉；停越久，整局越慢
另外找一塊地方顯示牌面可以馬上更新，不拖慢遊戲手機畫面很擠，多一塊固定區域就會壓縮牌面

最後的取捨是兩邊各做一點：

  1. 原地：0.4 秒拉長到 0.8 秒，並在三張牌的角落標出是誰拿的（自己是綠色、別人是藍色）。0.8 秒足夠看清是哪三張，又不會明顯拖慢節奏；而且這段時間其他人仍然可以選牌（見第 IV 節），不會卡住任何人。
  2. 畫面上方的浮動提示：「小明 找到一組 SET」，下面附上那三張牌的縮圖，停留約 2.6 秒。它浮在畫面最上方，不佔牌面的空間；牌面換掉之後，仍然看得到剛剛被拿走的是哪三張。

這兩者都不會改變牌面大小。唯一新增、會佔空間的是玩家名單；手機版把它固定成一行、可以左右滑動，人再多也不會換行擠壓牌面。

VI. 斷線重連：回到同一局

手機螢幕一關、切去回個訊息，連線就很容易斷掉。所以斷線之後，用同一個房號回來，要能接續原本的牌局，而不是重開一局：

情況會發生什麼
有人斷線房主保留他的分數，名單上標成「離線」；所有人都離線時暫停計時。斷線的人畫面會出現「要重新加入房間 XXXX 嗎？」，按一下就回到原本的牌面和分數。
加入者重新整理頁面一打開就出現同樣的提示，按「重新加入」即可接續。
房主重新整理頁面出現「房間 XXXX 的牌局還在，要回去繼續嗎？」。按下後用同一個房號重新開房，牌面、牌堆、每個人的分數、時間都還在，等大家重新加入。
換了分頁或瀏覽器，用同一個暱稱回來接回原本的分數，名單上不會多出一個同名的人（見問題 #23）。
新的人加入從 0 分開始加入這一局，不會接手別人的分數。同一個房間裡不能有兩個人同名。

要做到「同一個人回來才接續」，每個分頁會產生一個玩家代號，連上時第一則訊息就附上它。房主收到後比對：名單裡已經有這個代號，就把分數還給他；沒有的話就是新玩家。斷線前的牌局，房主會隨時存在自己的分頁裡（sessionStorage），所以重新整理也不會消失；同一個分頁重新整理，玩家代號也不會變。紀錄保留 30 分鐘，按「離開」或切換模式就會清掉。

對方回來得太快怎麼辦

手機睡著再醒來，可能在房主「還沒發現舊連線斷了」的時候就重新加入。房主以為對方還在線上，原本會把這個新連線當成第三個人擋掉。現在會先等新連線報上玩家代號：是同一個人，就直接換成新的連線、接續牌局；房間已經有 6 個人時，新的人才會收到「房間已滿」。

#1

電腦和手機怎麼試都連不上

症狀

建立房間正常，另一台輸入房間碼後一直顯示連線中，最後跳出「連線逾時」。

原因

程式為了多加一個 Cloudflare 的 STUN 伺服器，自己寫了一份 iceServers 設定。問題是這份設定會整個取代 PeerJS 的預設值，順便把 PeerJS 內建的 TURN 中繼伺服器也拿掉了。STUN 只能幫兩台裝置嘗試直接連線；只要有一方在手機網路或比較嚴格的路由器後面，直連打不通，本來應該改走 TURN 中繼，但中繼已經不存在了。

修法

把 PeerJS 的 TURN 中繼加回設定裡，並在程式旁邊註明「自訂這個設定會覆蓋預設值」，避免之後又有人重蹈覆轍。

驗證

在本機架一套 PeerJS 配對伺服器，用兩個瀏覽器實際對打完一整局，確認牌面、分數、結算兩邊一致。

#2

同一個 Wi-Fi 也連不上

症狀

加回 TURN 之後，電腦和手機在同一個租屋處的 Wi-Fi 下，還是出現「已找到房間，但雙方網路打不通」。

原因

租屋處的路由器常會開「AP 隔離」，讓不同房客的裝置彼此看不到，所以就算在同一個 Wi-Fi，兩台裝置也不能直接互傳資料。這時只能靠中繼，但 PeerJS 那組免費 TURN 沒有任何可用性保證，實際上也沒有接住。

修法

新增 MQTT 備援通道（見「連線對戰」第 II 節）：直連 10 秒打不通，就自動改由公開的 MQTT 伺服器轉送。另外，如果 PeerJS 的配對服務本身連不上，房主也能只靠備援通道開房。

驗證

模擬三種情況：直連被擋住、正常直連、配對服務整個掛掉，三種都能連上並完成對局、重新開始，也能偵測對方關掉分頁。上線後實際用電腦和手機，確認是經由備援伺服器連上的。

心得

免費的公共服務能當備援，但不能當唯一的路。這次的解法是讓兩條路互相補位，任一條掛掉，遊戲都還能玩。

連線：狀態互相覆蓋

#3

按了「離開」卻顯示「連線中斷」，有時還把新的連線搞壞

症狀

按離開後，狀態列不是「已離開」，而是「連線已中斷，請離開後重新加入」。另外，前一次沒打通的連線晚一點才宣告失敗時，會把剛剛連上的新連線一起標成斷線。

原因

每條連線都有自己的「關閉」事件，但處理這個事件時，沒有先確認「這還是目前正在用的那條連線嗎」。PeerJS 關閉連線時又可能立刻觸發事件，所以離開時，程式自己關掉連線，接著又被自己的關閉事件覆蓋了狀態。

修法

事件處理一律先檢查「是不是目前的連線」，舊的連線一律忽略；離開時先把參照清空，再關閉連線。房主那邊，如果有一條還沒打通、卡在半路的連線，新的加入請求來了就直接取代它。

驗證

用兩個瀏覽器測試：離開、對方離開、重新加入、加入不存在的房間，每種情況的狀態文字都正確。

對戰：選錯會擋住對手

#4

我選錯的那半秒，對手明明選對了卻被拒絕

症狀

房主選錯三張，紅框閃爍的那 0.5 秒內，加入者送出的正確答案被回「另一位玩家更快」。

原因

「選錯的動畫」和「有一組 SET 正在結算」共用了同一個鎖。選錯只是本機的視覺效果，卻讓房主以為整個牌局正在結算，所以拒絕了所有搶答。

修法

拆成兩個狀態：「正在結算」才會擋住搶答；「選錯動畫」只擋住自己繼續點牌，不影響對手。

驗證

讓房主刻意選錯，同時讓加入者送出正確答案，確認加入者正常得分。

#5

對手一得分，我選到一半的牌全部被取消

症狀

正在選第二張牌時，對手剛好拿走一組 SET，自己的選取整個被清空，要重選。

原因

每次牌面更新，程式都直接把選取清空，不管選到的牌還在不在。

修法

只取消「已經不在檯面上」的牌，其他的保留，並透過提示告訴你對手用掉了你選的幾張。

驗證

讓加入者先選 2 張，房主拿走包含其中 2 張的 SET，確認提示文字正確，且被拿走的牌已取消選取。

對戰：合法搶答被誤判

#6

補完牌的瞬間送出的答案被拒絕，牌被拿走時還被說成「不是 SET」

症狀

有人剛補牌的一瞬間，另一方送出的三張牌明明都還在檯面上，卻被拒絕。另外，牌剛被對手拿走時送出的請求，會被回報成「這三張不是 SET」，玩家會以為自己看錯。

原因

房主原本用「牌面版本號」判斷請求是否過期，只要版本不同就一律拒絕。但補牌只會新增牌，不會動到原本的牌。另外，「牌已經不在檯面上」和「三張不構成 SET」原本走同一個錯誤分支。

修法

改成只檢查「是不是同一局」以及「三張牌是否都還在檯面上」。錯誤原因也分成三種代碼：舊局、正在結算、不是 SET，加入者依代碼顯示不同提示。

驗證

補牌後立即送出原有的三張合法牌，確認能得分；搶輸時顯示「對手比你快一步」，而不是「不是 SET」。

#7

只有房主看得到最後比分

症狀

遊戲結束時，房主跳出「遊戲結束，13：12，你贏了！」，加入者那邊什麼都沒有。

原因

結算視窗寫在「判斷遊戲結束」的函式裡，而這個函式只在房主那邊執行。加入者只收到一份「遊戲已結束」的牌面。

修法

加入者收到「遊戲已結束」的牌面時，用自己的角度顯示結果（你贏了／房主獲勝）；同一局只顯示一次。

驗證

讓兩個瀏覽器自動打完一整局，確認兩邊的比分互為相反、結果都正確。

對戰：自動補牌與重新開始

#8

開局就是 15 張，而且大家不知道系統會自己補牌

症狀

對戰一開局常常就是 15 張，玩家不確定檯面無解時系統會不會處理，只能乾等。

原因

對戰模式原本會在每次發牌後檢查，只要無解就偷偷一直補，直到有解為止，玩家完全看不到這個過程。

修法

取消自動補牌，改成「沒有 SET？補牌」按鈕（見「連線對戰」第 III 節）。開局固定 12 張，是否無解交給玩家判斷。電腦對手找不到解時，也會按同一顆按鈕。

驗證

測試四種情況：有解時按（兩邊都看到剩幾組、不補牌）、無解時按（兩邊都補到 15 張）、2 秒內連按、電腦自己按。

#9

一方按「重新開始」，整局就被洗掉

症狀

手機上手滑碰到「重新開始」，兩個人的牌局直接作廢。

原因

加入者按重新開始，會直接要求房主開新局；房主按的話更是立刻開始，對方沒有任何拒絕的機會。

修法

改成邀請制（見「連線對戰」第 III 節）。單人和電腦模式打到一半時按重新開始，也會先確認一次。

驗證

測試邀請、拒絕、取消、逾時、同意、兩邊同時按，以及單人模式的確認與取消，每種情況牌面都符合預期。

對戰：結束後與同時搶答

#10

遊戲結束後拒絕「再來一局」，對方卻看到「對手想繼續這局」

症狀

雙人連線打完一局，一方邀請再來一局，另一方按「先不要」，邀請的人收到的提示是「對手想繼續這局」，但這局其實已經結束了。測試時還發現：被邀請的那一方，提示列被「遊戲結束」的比分視窗蓋住，必須先關掉比分視窗才點得到。

原因

拒絕的提示只有一種寫法，沒有考慮牌局是否已經結束。提示列的圖層又比比分視窗低，被整個蓋住。另外，對方 20 秒沒回應而自動拒絕時，邀請方也會看到同一句話，分不出是「拒絕」還是「沒回應」。

修法
  • 牌局已結束時拒絕，顯示「對手不想跟你玩了」；進行中拒絕才顯示「對手想繼續這局」。
  • 自動拒絕時會附上原因，邀請方看到的是「對手沒有回應」。邀請方多等 3 秒，讓對方的自動拒絕先送到，兩邊不會各說各話。
  • 提示列的圖層提高到比分視窗之上；送出邀請時，自己的比分視窗會自動關閉，換成等待提示。
  • 遊戲結束後，「沒有 SET？補牌」會隱藏（已經沒有意義），「重新開始」改名為「再來一局」並以主色顯示。
  • 對方按同意時，邀請剛好已經失效，會收到「邀請已經失效，請重新邀請」，而不是按了沒反應。
驗證

測試版本只發 18 張牌，讓兩個瀏覽器自動打完一局，再測試邀請、拒絕：被邀請的一方可以直接點到提示列（不必先關比分視窗），邀請方看到「對手不想跟你玩了」。

#11

兩人同時找到不同的 SET，後到的人點了沒反應

症狀

對手剛拿走一組 SET 的那 0.4 秒內，另一方去點另一組完全不相干的 SET，點下去什麼都沒發生，連選取都沒出現；等畫面更新再點，可能已經來不及。

原因

為了修 #19 的重複計分問題，程式在「有 SET 正在結算」時會擋掉所有點擊。但那次要擋的只是「自己的 SET 正在結算時」的點擊；對手的 SET 正在結算時，自己去選別張牌是完全合理的。房主那邊也有對應的問題：結算中收到加入者的搶答，會直接以「另一位玩家更快」拒絕，就算兩組牌毫無重疊。

修法
  • 只有「自己的 SET 正在結算或等待結果」時才鎖住操作；對手的 SET 結算中，仍然可以選牌，點到被拿走的牌會提示，被拿走的牌也會立刻從選取中移除。
  • 結算中收到的搶答不再拒絕，而是先排隊，結算完用新的牌面依序判定：牌都還在、而且是 SET，就照樣得分。
  • 加入者送出的搶答還在排隊時，畫面更新不會解除等待狀態，避免同一組牌被重複送出。
  • 電腦對戰套用同一套規則：電腦剛搶到時，玩家立刻選另一組也會算分。
驗證

讓一方先拿一組 SET，另一方在 0、0.05、0.2 秒後拿另一組不重疊的 SET，房主先和加入者先兩個方向都測，雙方都各得一分。同時確認原本的保護沒有失效：自己的 SET 結算中多點三張牌，分數只加一次、牌堆只少三張。

心得

修一個 bug 時加上的保護，範圍要剛好。「擋住所有點擊」解決了重複計分，卻順便擋掉了對手結算時的正常操作；真正需要擋的，只有「自己」那 0.4 秒。

#12

重新開始前送出的搶答，在新的一局裡跳出「對手比你快一步」

症狀

選牌選到一半剛好開了新局，有時會在新局一開始看到莫名其妙的「對手比你快一步」。

原因

上一局送出的搶答，結果在新局開始後才送到，加入者把它當成這一局的結果處理。另外，房主在對局結束後收到搶答時不會回覆，加入者要等 5 秒逾時才會解除等待。

修法

房主的每個回覆都附上局次，加入者忽略不屬於目前這局的結果；並且只認「自己最後送出的那一次搶答」的結果。對局已結束時，房主會明確回覆，加入者立即解除等待。

對戰：斷線與排版

#13

斷線後用同一個房號回來，卻直接開了新的一局

症狀

加入者手機螢幕關掉、連線中斷，回來用同一個房號加入，原本打到一半的牌局沒了，直接變成新的一局。

原因

房主只要有人連進房間，就一律開新局，完全不管之前打到哪裡。對手斷線時，房主還會把所有計時器清掉，如果剛好有一組 SET 正在結算，那組也會卡在一半。另外，加入者重新整理後完全不記得自己在哪個房間；房主重新整理，整局就消失了。

修法
  • 對手斷線時，房主保留牌局：暫停計時，正在結算的那組讓它跑完，並把整局存在分頁裡。
  • 每個分頁有自己的玩家代號，房主據此判斷回來的是不是同一個人：是就接續，不是就開新局。
  • 加入者斷線或重新整理後，會出現「重新加入房間 XXXX」的提示；房主重新整理後，可以用同一個房號恢復牌局。
  • 加入者收到牌面後，狀態列會從「同步中」改成「已連上房主」或「已重新連上房主，繼續剛才的牌局」。原本會一直停在「同步中」。
驗證

在直連和備援通道下各測一次：加入者重新整理後重新加入、房主重新整理後恢復房間再讓加入者回來，兩種情況的牌面、比分都和斷線前完全相同，之後也能繼續對戰；斷線期間房主的計時器停住不動。換一個新的人用同一個房號加入，則會開新局。

#14

對方分頁直接被關掉，房主 30 秒後才發現，新的人被擋成「房間已滿」

症狀

加入者的分頁直接消失（手機沒電、瀏覽器被系統關掉）後，房主過了 30 秒以上才顯示對手離線。在這之前，任何人用這個房號加入都會看到「這個房間已經有兩位玩家了」；就算是原本那個人回來也一樣。

原因

直連沒有收到正常的關閉訊號時，要等底層的連線檢查逾時，通常超過 30 秒才會判定斷線。這段時間內，房主一直以為對手還在。

修法
  • 兩條路都加上心跳：每 5 秒互傳一次，20 秒沒收到就判定斷線。從背景切回來時，也會立刻補送一次。
  • 有人加入時，如果舊連線已經 8 秒以上沒有任何訊息，就當作已經斷了，直接讓新的人進來。
  • 舊連線看起來還活著時，先比對玩家代號：是同一個人就換成新連線並接續。
驗證

把加入者的瀏覽器直接關掉：房主在約 22 秒後顯示對手離線，新的人可以正常加入並開新局。另外模擬「同一個人立刻回來」：直連約 1 秒、備援約 11 秒就接回原本的牌局，牌面和比分都相同。

#15

電腦版補牌後，牌面從 4×3 突然變成 6 欄

症狀

電腦版原本是 3 列 × 4 欄。補到 15 張後，有時變成一排 6 張共兩排、再多 3 張（2×6+3），有時變成 4 列；每張牌的位置全部換過，要重新找一遍。

原因

每次張數改變，程式都會在幾種欄數之間重新挑一個「卡片最大」的排法，而 12 張和 15 張挑出來的結果不一樣。

修法

照實體 SET 的擺法：先用 12 張決定排法，之後補牌、縮編都沿用同一種，只會在同一個方向延伸：

  • 電腦版和手機橫拿：固定列數，牌由上往下、一欄一欄排。補 3 張就是在右邊多一欄，原本 12 張的位置完全不動；拿走一組之後，最右邊那一欄會收回去。
  • 手機直拿：固定 3 欄，補 3 張就是在下面多一列。

因為改成由上往下排，電腦版的牌號順序也改成直的：#2 在 #1 的下面。

驗證

在 1366×768、1920×1000、1280×650、手機直拿、手機橫拿下，比較 12 張和 15 張的排法：電腦版都是 4×3 → 5×3，手機直拿是 3×4 → 3×5，全部仍在同一個畫面內。

手機版：牌面塞不進一個畫面

#16

連線後要往下捲很久才看得到第一張牌

症狀

手機上連線之後，建立房間、加入房間、離開這些按鈕都還在，牌面的第一列被推到 600px 以下；牌面只排 2 欄，12 張要排成 6 列；「加入房間」按鈕被擠成直排。

原因

連線區只有一種版面，不分「開房前」和「連線中」；牌面在窄螢幕直接降成 2 欄；按鈕允許換行。

修法
  • 連線後，設定區收成一行狀態加「離開」按鈕，牌面因此往上移了大約 460px。
  • 牌面改成依照螢幕剩下的高度自動計算卡片大小，從 3、4、6 欄裡挑出卡片最大的排法：直拿手機是 3 欄 × 4 列，橫拿自動變成 6 欄 × 2 列。（補牌時的排法後來又調整過，見 #15。）
  • 所有按鈕不換行；還沒連線時，牌面位置改成顯示說明文字。
驗證

用 iPhone 14、iPhone SE（扣掉 Safari 網址列後的高度）、一般 Android、手機橫拿四種尺寸量測，12 張牌與按鈕都在同一個畫面內，沒有左右捲動。補到 15 張的情況也另外驗證過。

#17

房主和加入者的卡片大小不一樣

症狀

在 iPhone SE 上，房主的卡片寬 92px，加入者卻是 112px。

原因

手機版外層的排版沒有把內容區撐滿寬度，所以內容區的寬度會跟著牌面縮放。偏偏計算卡片大小時，又是拿內容區的寬度來算，兩者互相牽動：牌一變小，內容區跟著變窄，下一次計算又更小。

修法

窄螢幕時，外層一律撐滿寬度，切斷這個循環；另外監聽上方區塊的高度變化（例如狀態文字換行），一有變化就重新計算。

驗證

四種尺寸重新量測，房主和加入者的卡片尺寸完全相同。

心得

「拿 A 的尺寸去算 B，而 A 又受 B 影響」這種循環，在單一尺寸下很難察覺，要換好幾種尺寸量才會現形。

#18

桌機對戰時，牌大到超出螢幕

症狀

解答面板只在單人模式出現之後，桌機對戰時牌面變成整個寬度，每張卡寬 321px，按鈕被擠到螢幕外。

原因

桌機的牌面原本固定 4 欄並撐滿寬度，以前旁邊有解答面板分掉寬度，所以沒出過問題。

修法

同一套自動計算也用在桌機上，並限制每張卡最寬 280px。

驗證

在 1366×800 和 1920×1000 下，牌和按鈕都在同一個畫面內。

多人：名次與版面

#19

比分視窗擋住「再來一局」，要多按一次

症狀

遊戲結束時跳出比分視窗，想再來一局得先按「確認關閉」，再去按下方的按鈕。被邀請的人也一樣，邀請列被視窗蓋住，看不到「同意」。

原因

比分視窗是蓋住整個畫面的對話框，只有一個關閉按鈕；邀請列的層級比視窗低。

修法

遊戲結束時，比分視窗裡直接放「再來一局」，原本的按鈕改成「先看一下牌面」；邀請列提高到視窗之上。

#20

同分的兩個人，一個拿金牌、一個拿銀牌

症狀

三人局 1：1：0 結束，比分視窗顯示「🥇 你 1　🥈 小明 1」，明明同分卻分了高下。

原因

獎牌是依排序後的位置發的，排在前面的就拿金牌。

修法

名次改成「比自己高分的人數 + 1」，同分同名次（1、1、3），標題也會寫「並列第一」。

#21

玩家名單一換行，手機上的牌就縮小一截

症狀

四個人連線時，iPhone SE 上的名單排成兩行，卡片從 113px 縮到 87px。

原因

名單會自動換行，多出來的那一行高度全部從牌面扣掉。

修法

手機版名單固定成一行、可以左右滑動。開局後，房間碼方塊也會收起來（狀態列仍寫著房號），只在等待室時顯示，方便分享。

驗證

同一台 iPhone SE，4 人時卡片回到 101px，12 張牌仍在同一個畫面裡。

#22

有人中途加入，牌面就重排

症狀

電腦版開局後又有人加入，連線區的高度改變，牌面跟著從一種排法跳到另一種。

原因

每次重算排法時，都會用「目前上方區塊的高度」去挑卡片最大的排法。名單、狀態文字一變高，算出來的結果就不同。

修法

同一局、同樣的視窗大小，排法只決定一次，之後只沿用；只有開新局或視窗大小改變時才重算。

#23

斷線回來，名單多出一個同名的人，分數也歸零

症狀

手機關掉分頁、重新點開網址再加入，名單上出現兩個「小明」：一個離線、還留著原本的分數；另一個在線、從 0 分開始。斷越多次，名單越長。

原因

房主是靠「玩家代號」認人的，而代號存在分頁裡：同一個分頁重新整理會保留，但關掉分頁、換一個瀏覽器，就會產生新的代號，房主只能把他當成新玩家。

修法

代號對不上時，再用暱稱比對一次：

  • 名單上有同名的人已經離線：直接把他的分數、牌型統計、投票狀態搬到新代號，視為同一個人回來。
  • 同名的人看起來還在線：可能是舊連線還沒被發現斷了，也可能真的是另一個人。房主先問舊連線一聲，2.5 秒內沒有回應就當作已經斷了，照上面的方式接回；有回應就請新來的人換個暱稱。
  • 跟房主同名也會請對方換一個。
驗證

關掉分頁後立刻用同一個暱稱重新加入，約 2.5 秒後接回原本的分數，名單維持 3 個人；兩個人同時在線且同名時，後來的人會看到「房間裡已經有人叫「阿華」了」。

心得

用暱稱認人，代價是任何人只要知道房號和暱稱，就能接手一個離線玩家的分數。對朋友間的小遊戲，這比名單越來越長、分數不見更能接受。

早期修掉的問題

#24

分數莫名其妙多一分，還白白吃掉三張牌

症狀

偶爾分數多算一分，牌堆少了三張，結算時的 SET 類型也多記了一組。

原因

配對成功後，會先亮綠框 0.4 秒才真正處理資料。這 0.4 秒內沒有上鎖，手快多點一張牌，就會再觸發一次判定，用舊的位置把剛補上的三張新牌又挖掉一次。

修法

加上「結算中」的鎖：點牌和判定的入口都會檢查，重新開始時也會解鎖，避免在動畫中按重新開始，導致遊戲永久卡住。

驗證

用程式模擬點擊：連點三張觸發判定後，在動畫期間點第四張，確認選取數與分數都沒變，動畫結束後也能繼續操作。

心得

這類跟時間差有關的 bug，人工測試幾乎抓不到，因為人看到綠框會自然停手。只能靠程式模擬精確的點擊時機。

#25

提示面板的條紋圖案有時變透明

症狀

解答面板裡的縮圖，在檯面更新後，條紋紋路的牌會變成空心。

原因

條紋圖樣用「牌的編號」命名。面板縮圖和檯面上的牌是同一張，產生了重複的名稱；縮圖其實一直借用檯面上的那份圖樣，檯面一重畫，那份圖樣就不見了。

修法

面板縮圖的圖樣名稱加上獨立的前綴，和檯面完全分開。

#26

牌堆剩 1～2 張時，補牌會多出空格

症狀

快結束時無解補牌，檯面尾端出現空白的格子。

原因

補牌固定補 3 次，但牌堆只剩 1～2 張時，後面幾次補進的是空值。

修法

有幾張補幾張，補完之後再檢查一次遊戲是否結束，因為牌堆可能剛好抽乾而且仍然無解。

本頁重點
  1. 我知道、但還沒處理的事
  2. 為什麼把這些寫出來

我知道、但還沒處理的事

  • 房主把分頁關掉，房間就消失。整局的狀態只存在房主的瀏覽器裡。重新整理（或手機瀏覽器在背景自動重新載入）可以在 30 分鐘內恢復同一個房號；但分頁整個關掉、或換一台裝置，就沒有伺服器可以接手了。這是不架後端換來的代價。
  • 房主有一點天生的優勢。房主點牌不用經過網路，大約領先一趟傳輸時間；走備援通道時差距會再大一點。
  • 加入者之間不直接相連。所有訊息都經過房主轉送，6 個人時房主要同時維持 5 條連線，房主的網路最吃重。
  • 暱稱就是身分。換了分頁的人靠暱稱接回分數，所以知道房號和暱稱的人，也能接手一個離線玩家的分數（見問題 #23）。
  • 名次只看分數。沒有考慮找到的速度或選錯次數，同分就並列。
  • 備援伺服器是公開的。理論上別人看得到牌局訊息和暱稱（暱稱不要用真名），也可能被惡意送入假的請求（房主仍會驗證每一個請求，所以最多是干擾，不會被亂加分）。
  • 提示面板的「滑過高亮」只支援滑鼠。觸控裝置看不到對應的高亮，應該補上點擊與焦點事件。
  • 顏色是規則的一部分，但沒有色盲輔助。紅綠色盲的玩家很難分辨紅色和綠色的牌，應該提供文字標示模式或改用色盲友善的配色。
  • 補牌時牌序會反過來（見「遊戲核心」第 VI 節），功能正確，只是視覺上不夠直覺。

為什麼把這些寫出來

把「我知道但還沒做」和「我不知道」分開，前者是待辦清單，後者才是真正的風險。這一頁的每一個修正，都是先有人回報「這裡怪怪的」或測試抓到異常，再回頭追原因；把限制寫清楚，下一個問題出現時就知道該從哪裡找起。
