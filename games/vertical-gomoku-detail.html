Gravity Search

立式五子棋：用重力壓縮行動空間，再以時間受限的 Alpha-Beta 搜尋做決策
棋盤 9 × 8 合法行動最多 9 評估窗口 116 AI 深度最高 7 Hard 預算 240 ms
本頁重點
  1. 為什麼重力讓五子棋變成另一個問題
  2. O(1) 落子：盤面加一個 heights 向量

I. 重力改變了問題的形狀

一般五子棋每一手可以放在任何空格；立式五子棋則只能選擇欄位，棋子會落在該欄最低空格。這不是單純加一個動畫，而是把狀態空間的分支因子整個改掉：

一般 9×8 五子棋

空盤第一手有 72 個合法位置，第二手 71 個。深度 4 的暴力樹約為 $72\times71\times70\times69$，超過 2,400 萬個節點。

重力式 9×8 五子棋

不論盤面多空，一手最多只有 9 個欄位。深度 4 的粗略上界是 $9^4=6,561$；滿欄後還會繼續下降。

重力同時帶來新的戰術限制：某個看似可以補成五連線的空格，如果下方還有空位，玩家根本無法立刻放到那裡。AI 因此不能只看「幾顆連在一起」，還必須透過真正的落子函式產生合法後繼狀態。

合法 action 是欄位 0–8，不是 72 個格子的任意座標

II. O(1) 落子：盤面加一個 heights 向量

盤面用長度 72 的 Int8Array 表示，索引公式是 row * 9 + col。除此之外另存一個長度 9 的 heights，記錄每欄已經有幾顆棋子：

state.js
function createState() {
    return {
        cells: new Int8Array(ROWS * COLS),
        heights: new Int8Array(COLS),
        turn: P1, moveCount: 0, lastMove: -1
    };
}

若沒有 heights，每次選欄都要從底部向上掃到第一個空格，最壞 $O(R)$。有了欄高，落點直接由公式得到：

$$ row = ROWS - 1 - heights[col] $$
drop-and-undo.js
function drop(st, col) {
    if (st.heights[col] >= ROWS) return -1;
    const row = ROWS - 1 - st.heights[col];
    const idx = row * COLS + col;
    st.cells[idx] = st.turn;
    st.heights[col]++;
    st.turn = 3 - st.turn;
    return idx;
}

undoDrop() 逐項反轉這些操作。這不是附帶功能，而是搜尋正確性的地基：AI 在同一份狀態上反覆「落子 → 遞迴 → 還原」，若有任何欄高、回合或最後落點沒有復原，後面的搜尋結果都不可信。本次開發以 Node.js 一次性腳本對 3,000 個隨機局面執行 drop/undo，逐位元組比對前後快照，全部一致。

III. 勝負判定只從最後落點向外掃

每次落子後，盤面上唯一新增的連線一定包含剛落下的那顆棋子。因此不必重掃全盤，只要從最後落點往四組方向延伸：

方向向量代表方向雙向掃描
[0, 1]橫向左／右
[1, 0]直向上／下
[1, 1]下降斜線左上／右下
[1, -1]上升斜線右上／左下
winningCells.js
for (const [dr, dc] of DIRECTIONS) {
    const line = [lastIdx];
    for (const sign of [-1, 1]) {
        let r = row + dr * sign;
        let c = col + dc * sign;
        while (inBounds(r, c) && st.cells[indexOf(r, c)] === player) {
            line.push(indexOf(r, c));
            r += dr * sign; c += dc * sign;
        }
    }
    if (line.length >= 5) return line;
}

它同時回傳完整連線，UI 可以直接把五顆或更多棋子全部高亮。本次一次性核心驗證涵蓋橫、直、兩種斜向與六連線，不只測最常見的橫向案例。

IV. 盤面共有 116 個評估窗口

勝負判定可以從最後落點局部掃描；但 AI 的靜態評估要知道全盤有哪些潛在五連線，因此枚舉所有長度恰為 5 的窗口：

$$ 8(9-5+1) + 9(8-5+1) + 2(8-5+1)(9-5+1) = 40 + 36 + 40 = 116 $$

每個窗口若同時有雙方棋子，就已被封死而不計分；只含單方棋子時依數量給分。這 116 個窗口是後面 AI 評估函式的完整幾何基礎。

V. 戰術底線放在搜尋之前

深度受限的 AI 最大風險，是因為時間到或難度隨機而漏掉「下一手就結束」的局面。因此選步流程先做兩個不受難度影響的檢查：

  1. 逐欄模擬自己的落子；若任何一欄立即連五，直接下，不進搜尋。
  2. 把回合暫時切成對手，逐欄測試；若對手下一手可連五，立即封鎖。
  3. 只有沒有立即勝負時，才進入難度隨機與 Alpha-Beta 搜尋。
簡單不等於故意看不見

簡單難度有 34% 機率隨機選合法欄，但這個隨機分支在戰術檢查之後。它可能在長期布局上犯錯，卻不會放棄眼前已經完成的五連線，也不會無視你下一手的明顯勝局。

VI. Iterative Deepening + Negamax + Alpha-Beta

核心搜尋使用 negamax：零和賽局裡「我的分數」等於「對手分數的負值」，所以 minimax 的 max/min 兩套遞迴可以合併成一個函式：

$$ V(s) = \max_{a \in A(s)} \big(-V(T(s,a))\big) $$

Alpha-Beta 維護目前已知下界 $\alpha$ 與上界 $\beta$；當 $\alpha \ge \beta$ 時，後續分支不可能改變祖先決策，可以直接剪掉。

iterative-deepening.js
for (let depth = 1; depth <= maxDepth; depth++) {
    try {
        const result = searchWholeLayer(depth);
        bestMove = result.move;      // 只有完整跑完這層才採用
        completedDepth = depth;
    } catch (TIMEOUT) {
        break;                           // 保留上一層完整答案
    }
}

Iterative deepening 不是重複浪費工作：前一層找到的最佳欄位會在下一層優先搜尋，讓 Alpha-Beta 更早取得高品質的 $\alpha$，通常能剪掉更多分支。時間到時，AI 至少持有上一個完整深度的答案，不會拿「只搜尋一半」的偏頗結果。

VII. 三個讓搜尋真的跑得動的細節

1. Move Ordering：從中央向外

欄位順序固定為 [4,3,5,2,6,1,7,0,8]。中央欄參與的橫向與斜向窗口最多，通常也是較好的走法。先找到好走法不改變答案，卻會大幅提高 Alpha-Beta 的剪枝率。上一層搜尋的最佳欄還會被提升到第一順位。

2. Transposition Table

不同落子順序可能到達同一個盤面。快取表以「72 格內容 + 輪到誰」為 key，保存搜尋深度、分數、上下界旗標與最佳走法。這裡不用隨機 Zobrist hash，而使用完整三進位字串；配置成本較高，但保證沒有 hash collision，小型前端遊戲更重視可靠性。

3. 降低時間檢查成本

每個根候選與新深度開始前都無條件讀取時鐘；遞迴內則利用位元運算 (nodes & 63) === 0，每 64 個節點檢查一次。這是目標時間預算而非作業系統層級的硬 deadline：單一節點不能被中途打斷，但比原本每 512 節點檢查更能限制慢速裝置上的超時誤差。

VIII. 局面評估：窗口分數必須反對稱

深度到底後尚未分出勝負，就計算 116 個窗口。窗口內同時有雙方棋子時價值為零；只有一方時使用非線性分數：

同色棋子數分數意義
12非常弱的潛力
213開始成形
395需要關注的威脅
42,200接近決勝；若落點可達通常必須處理
51,000,000理論終局（正常會更早由勝負判定攔截）

對手窗口使用完全相同的權重再取負值，讓評估函式滿足 Negamax 必要的反對稱條件：

$$ evaluate(s,p) = -evaluate(s,3-p) $$

如果為了「偏重防守」而只把對手分數乘上 1.08，交換玩家後就不會恰好變號，搜尋深度的奇偶會讓攻守偏好反轉。要保留 Negamax 的正確語意，攻守權重必須對稱。棋子越靠近中央欄仍會取得較高位置分，但這項分數同樣以正負對稱計算。

IX. 非同步競態：舊 AI 不能落到新棋局

AI 為了讓玩家看清落子，會延遲 360ms 才開始搜尋。這創造了一個常見競態：玩家落子後立刻按「重新開始」或切換難度，舊的 timer 若未取消，就可能在新棋局裡莫名下一顆棋。

session-token.js
let sessionId = 0;
let aiTimer = null;

function scheduleAi() {
    const token = sessionId;
    aiTimer = setTimeout(() => {
        if (token !== sessionId) return;
        const result = chooseAiMove(cloneState(state));
        if (token !== sessionId) return;
        finishMove(...);
    }, 360);
}

function cancelAi() {
    sessionId++;
    clearTimeout(aiTimer);
}

這裡同時使用兩層防護：clearTimeout 取消已知 timer；單調遞增的 session token 防止已經進入 callback 的舊工作提交結果。本次開發以 Headless Chrome 一次性驗證：在 AI 等待期間切換設定，等待 850ms 後新盤仍為 0 顆棋子。

X. 棋子不能反過來撐大棋格

站上另一款棋類遊戲曾在 iOS Safari 發生過：aspect-ratio 容器裡的流內 SVG 使用 height:100%，Safari 把它退回替換元素預設的 150px 高，結果第一顆棋子一出現，整個棋盤突然變大並壓到按鈕。

這款遊戲從一開始就不用流內圖片：棋子由 .cell::after 偽元素繪製，並以 position:absolute; inset:10% 完全脫離排版流。棋格尺寸只由 CSS Grid 和棋盤 aspect ratio 決定，棋子永遠無法反過來影響它。

行動版一次性實測

開發環境為 macOS Headless Chrome；430、390、375、320px 四種模擬寬度都驗證：無水平溢出、棋格保持正方形、觸控落子與 AI 回應後棋盤及棋格尺寸逐像素不變。這些驗證腳本不屬於靜態網站部署內容。

XI. 誠實的已知限制

  • Hard 不是完美解。它最多搜尋 7 層並使用啟發式評估，不是完整解出 9×8 的賽局；足夠有挑戰性，但不能宣稱不可戰勝。
  • 搜尋仍在主執行緒。Hard 最壞可能佔用約 240ms，期間動畫會短暫停頓。更進一步應把純搜尋核心移入 Web Worker；目前以時間預算換取單檔實作的簡潔。
  • Transposition key 會配置字串。完整盤面字串沒有碰撞，卻帶來配置與 GC 成本。更大的棋盤應改用 64/128-bit Zobrist hash，並接受極低的碰撞風險。
  • 沒有悔棋。AI 模式的悔棋應一次撤回玩家與 AI 兩手，還要處理「AI 正在等待」的競態；目前只提供重新開始。
  • 啟發式不理解所有重力可達性。窗口分數知道幾顆同色，卻不直接估算窗口中空格距離目前欄高還差幾層；深度搜尋會修正近程錯覺，但葉節點評估仍可能高估懸空威脅。
