I. 出題：Fisher–Yates 與被浪費的六次交換

題目是「四位不重複的十進位數字」，允許前導零（0123 是合法答案）。因此解空間就是十取四的排列數：

$$ |S| = P(10,4) = \frac{10!}{6!} = 5040 $$

出題函式沒有用「隨機抽 → 檢查重複 → 重抽」的拒絕採樣（rejection sampling），而是直接對整個數字池做 Fisher–Yates 洗牌後切片。這保證了 O(1) 的最壞執行時間，不會像拒絕採樣那樣有理論上的無限迴圈風險：

genSecret.js
function genSecret() {
    const d = '0123456789'.split('');
    for (let i = d.length - 1; i > 0; i--) {
        const j = Math.floor(Math.random() * (i + 1));
        ;[d[i], d[j]] = [d[j], d[i]];
    }
    return d.slice(0, 4).join('');
}

兩個藏在細節裡的東西

  • 那個孤零零的分號是必要的。陣列解構交換 [a, b] = [b, a] 以左方括號開頭。JavaScript 的自動分號插入（ASI）不會在上一行結尾補分號，於是 ...(i + 1)) 後面緊接 [d[i], ...] 會被解析成索引存取而不是新的敘述句。這是解構交換最經典的陷阱。
  • 洗了 9 次交換，只用到 4 個結果。完整洗牌是 $O(n)$，但這裡只需要前 $k$ 個元素。改成 partial shuffle（只跑 $k$ 圈）即可降到 $O(k)$，也就是 4 次交換而非 9 次。在 $n=10$ 的規模下這完全是雞蛋裡挑骨頭，但它是「知道可以更好，選擇不做」與「不知道」的差別。
純前端遊戲的固有限制

Math.random() 不是密碼學安全的隨機源，而答案就存在瀏覽器的記憶體裡。任何人打開 DevTools 都能翻出答案。這是所有「答案在客戶端」的猜謎遊戲共有的性質 —— 要真正防作弊，判定必須搬到伺服器。這個專案的定位是練習與展示，所以刻意不處理。

II. A/B 判定：一行 else-if 背後的隱式契約

規則是 A = 數字對且位置對、B = 數字對但位置錯。整個判定只有兩行：

submitGuess.js
let a = 0, b = 0;
for (let i = 0; i < 4; i++) {
    if (current[i] === secret[i]) a++;
    else if (secret.includes(current[i])) b++;
}

資料結構就是兩個四字元字串，沒有 Map、沒有 Set、沒有計數陣列。外圈跑 $k$ 次，內層的 String.includes 是線性掃描，所以是 $O(k^2)$，$k=4$ 時等於 16 次字元比較 —— 常數時間。

但這個寫法在一般情況下是錯的

「位置不對就檢查存不存在」是網路上 1A2B 實作最常見的錯誤寫法。只要允許重複數字，它立刻崩潰：

答案 猜測 這段程式碼算出 正確答案
1123 1111 2A2B 2A0B
1234 1111 1A3B 1A0B

原因是 includes 只回答「有沒有」，不回答「還剩幾個沒被配對」。正確的通用解法要做多重集合的交集：

$$ \begin{aligned} A &= \sum_{i} [\,g_i = s_i\,] \\[4pt] A + B &= \sum_{d=0}^{9} \min\big(\text{cnt}_g(d),\ \text{cnt}_s(d)\big) \end{aligned} $$
general_solution.js
// 允許重複數字時的通用寫法：O(n + 10)，一次掃描
function judge(guess, secret) {
    const cg = new Array(10).fill(0);
    const cs = new Array(10).fill(0);
    let a = 0;

    for (let i = 0; i < guess.length; i++) {
        if (guess[i] === secret[i]) a++;
        // 位置對的也要計數，最後從交集扣掉才得到 B
        cg[guess[i]]++;
        cs[secret[i]]++;
    }

    let inter = 0;
    for (let d = 0; d < 10; d++) inter += Math.min(cg[d], cs[d]);

    return { a, b: inter - a };
}

III. 為什麼這段程式碼「剛好」是對的

既然那個寫法在一般情況下會算錯，為什麼這個遊戲玩起來完全正常？因為程式中存在兩道不變式（invariant），聯手把「重複數字」這個情況徹底排除掉了：

  1. 答案端：genSecret() 由洗牌後切片產生，四個數字必然互異。
  2. 猜測端：addDigit() 有一道守衛 if (current.includes(d)) return;，讓玩家根本無法輸入重複數字。

當雙邊都保證無重複時，每個數字的出現次數只會是 0 或 1，於是「存在」與「還有剩」等價，$\min(\text{cnt}_g, \text{cnt}_s)$ 退化成布林判斷 —— 簡化版與通用版在此完全等價。

這是本專案最值得記錄的脆弱點

addDigit() 裡那行重複檢查，看起來只是體驗上的貼心（避免玩家輸入無效組合），實際上卻是判定邏輯正確性的地基。任何人日後想加一個「進階模式：允許重複數字」，只要把那行拿掉，A/B 就會靜默算錯 —— 不會拋錯、不會當掉，只是答案變成錯的。

而原始碼裡沒有任何註解說明這件事。這種跨函式的隱式契約，就是所謂技術債裡最難察覺的一種：它不是寫得醜，而是正確性依賴一個沒有被記錄下來的前提。

若只是求「跑得動」

兩行 else-if，短、直觀、在現有規則下完全正確。閱讀成本最低。

若求「改得動」

用計數法，多 6 行但對任何長度、任何重複情況都成立，並且不對呼叫端做任何假設。

我保留了原本的寫法（它在現行規則下是對的，換掉純屬過度工程），但把這個前提寫進了這篇文章 —— 這正是技術文件該存在的理由。

IV. 資訊論下界：這遊戲最少要猜幾次？

每猜一次，玩家得到的資訊是一組 $(A, B)$ 回饋。先算出回饋的值域大小：$A + B \le 4$，且 $(A,B) = (3,1)$ 在數學上不可能發生（若有三個位置全對，第四個數字要嘛也對、要嘛不在答案裡，不可能「在答案裡但位置錯」）。窮舉所有 $5040 \times 5040$ 組合驗證後，實際會出現的回饋恰好是 14 種：

0A0B  0A1B  0A2B  0A3B  0A4B
1A0B  1A1B  1A2B  1A3B
2A0B  2A1B  2A2B
3A0B                       ← (3,1) 不存在
4A0B                       ← 過關
窮舉 5040 × 5040 = 25,401,600 組後得到的回饋值域

把猜謎看成一棵決策樹：每個節點分支數最多 14，要區分 5040 種可能，樹的深度下界是

$$ \lceil \log_{14} 5040 \rceil = \lceil 3.23 \rceil = 4 $$

也就是說，再聰明的策略都不可能保證在 4 猜內解出（而且 4 這個下界實務上達不到，因為回饋分布極不均勻 —— 大多數猜測得到的都是 0A1B 到 1A2B 附近的結果，資訊量遠低於理論上的 $\log_2 14 \approx 3.81$ bit）。

V. 實測：跑完全部 5,040 個答案

為了確認遊戲的判定邏輯真的自洽，我把頁面裡那段 A/B 程式碼原封不動抽出來，寫了一個候選集合過濾的求解器：維護所有仍與歷史回饋一致的候選答案，每次挑一個出來猜，再用回饋過濾。若判定邏輯有任何錯誤，候選集合會被過濾到空集合而爆掉。

solver_experiment.js
let cands = allPermutations;          // 5040 個
for (let t = 1; ; t++) {
    const guess = cands[0];
    if (guess === secret) return t;

    const fb = ab(guess, secret);
    // 只留下「若它是答案，會給出相同回饋」的候選
    cands = cands.filter(c => c !== guess && ab(guess, c) === fb);
}

對全部 5,040 個答案各跑一次，結果如下：

5,040 個答案的猜測次數分布，平均 5.56 猜、理論下界 4 猜
這個實驗證明了兩件事

一、判定邏輯完全自洽。5,040 次完整對局中沒有任何一次把候選集合過濾成空的，代表遊戲回報的 $(A,B)$ 與獨立實作的判定完全一致。

二、玩家的體感是有數據支撐的。純靠邏輯推理（不亂猜）的平均成績是 5～6 猜，這和理論下界 4 猜之間的差距，就是「回饋分布不均勻」的代價。所以遊戲裡的「最佳成績」顯示 4 以下時，那真的是運氣，不是實力。

VI. 變數驅動的絕對定位佈局

這頁的版面不是用 Flexbox 或 Grid 排的，而是用 CSS 自訂屬性推算出來的絕對定位。三個變數定義了整個佈局：

layout.css
:root {
    --center-panel-width: 500px;
    --right-panel-width: 260px;
    --panel-gap: 20px;
}

/* 共用外觀：垂直置中的玻璃擬態面板 */
.panel {
    position: absolute;
    top: 50%;
    transform: translateY(-50%);
    backdrop-filter: blur(15px);
}

.center-panel {
    width: var(--center-panel-width);
    left: 50%;
    transform: translate(-50%, -50%);  /* 覆寫基底 */
}

/* 🎯 右側面板的位置從中央面板「推導」出來 */
.right-panel {
    width: var(--right-panel-width);
    left: calc(50% + (var(--center-panel-width) / 2) + var(--panel-gap));
}

好處很實際：想把中央面板加寬 40px，只要改一個變數，右側面板會自己跟著讓位。壞處是它把一個幾何約束藏進了 CSS，而這個約束後來真的咬了我一口 —— 詳見「工程反省」那一頁。

單斷點的「拆解式降級」

行動版不是重新排版，而是把整套絕對定位機制整組拆掉：

  • html, body 的 overflow: hidden 解鎖成 auto（桌機版鎖死捲動是刻意的，因為版面剛好一屏）
  • .panel 改回 position: relative 並且 transform: none —— 這行最關鍵，忘了寫的話 translate(-50%, -50%) 會把面板推出畫面外
  • .game-area 改成 column flex，面板變成垂直堆疊

VII. 狀態流與渲染策略

整個遊戲的狀態只有六個變數，沒有框架、沒有 store、沒有 reducer：

變數 型別 角色
secret string(4) 本局答案
current string(0–4) 正在輸入的緩衝區
historyList Array<{guess, a, b}> 歷史紀錄，同時兼任回合計數器
gameOver boolean 閘門，散佈在 5 處檢查
wins / best number / number|null 跨局累積，initGame() 不重置

值得一提的是沒有獨立的回合計數器：猜測次數直接用 historyList.length 表示。少一個變數就少一個「兩份真相不同步」的機會，這種「能推導就不儲存」的取捨在小專案裡非常划算。

全量重繪，而且它是對的選擇

每次按鍵都會執行同一組三連呼叫：

render_flow.js
function addDigit(d) {
    if (gameOver || current.length >= 4 || current.includes(d)) return;
    current += d;
    renderDigits(); renderNumpad(); updateBtn();   // 全量重繪
}

每次重建 4 個數字格 + 10 個鍵盤按鈕 = 14 個 DOM 節點。這在效能上完全無感，換來的是狀態與畫面永遠不可能不一致 —— 沒有 diff 邏輯就沒有 diff 的 bug。這是小規模 UI 最被低估的架構選擇。

代價是每次重建都會讓焦點掉回 body，鍵盤使用者按數字鍵後會失去焦點位置；同一組三連呼叫也重複出現三次，抽成一個 renderAll() 會更乾淨。

VIII. 三個藏在 CSS 裡的巧思

1. 用 visibility 而不是 display 隱藏輸入區

猜中後要把輸入區藏起來、顯示結算視窗。這裡刻意用 visibility: hidden 而非 display: none：

結算視窗 #winArea 是 .center-panel 內的絕對定位元素。如果用 display: none 把輸入區從佈局流中移除，面板高度會瞬間塌陷，結算視窗就會浮在一個縮小的容器裡。visibility: hidden 保留了佈局盒子，面板高度不變，同時仍會把元素移出 tab order —— 兩個需求一次滿足。

2. 只寫 from 的 keyframe

popIn.css
#winArea {
    transform: translate(-50%, -40%);
    animation: popIn 0.4s cubic-bezier(0.17, 0.89, 0.32, 1.27);
}

@keyframes popIn {
    from {
        opacity: 0;
        transform: translate(-50%, -30%) scale(0.9);
    }
    /* 沒有 to：終點隱式取用元素自身的 transform */
}

省掉 to 不只是少打幾個字，而是避免了最終值被寫死兩次。之後想把結算視窗上移一點，只改 #winArea 一處即可，動畫終點會自己跟上。cubic-bezier 的第四個控制點大於 1，做出輕微過衝的彈跳感。

3. 用 unshift 換掉自動捲動邏輯

歷史紀錄用 historyList.unshift(...) 前插而非 push 後推。這代表最新一筆永遠在容器頂端，於是完全不需要 scrollIntoView() 或「捲到底部」的邏輯。代價是顯示回合編號時要用 historyList.length - idx 反推。用一次減法換掉一整塊捲動同步程式碼，很划算。

IX. 粒子背景：同一份程式碼的兩個世代

這頁的 canvas 背景和站上無限井字棋是同源程式碼，但是不同世代。放在一起看，剛好是一份自我審查紀錄：

特性 1A2B（早期） 無限井字棋（後期）
粒子數 固定 70 依螢幕寬度 34 / 90
粒子間連線 無 有，$d < 100$ 時畫線
滑鼠互動 無 150px 內產生吸引力
半徑 random()*1.5（可能為 0） random()*1.5 + 0.5
canvas 能力檢測 原本沒有 → 已補上 有

那個「半徑可能為 0」的問題很典型：Math.random() * 1.5 會產生趨近 0 的半徑，畫出看不見的粒子，等於白燒 CPU。後期版本加上 + 0.5 設下最小值。連線判定是 $O(n^2)$ 雙迴圈，90 顆粒子等於每幀 4,005 次距離計算，這也是為什麼後期版本要依螢幕大小降級。

X. 工程反省：我在這頁修掉的東西

這個專案寫完一段時間後，我用 headless Chrome 對全站做了一輪自動化檢查（量測各尺寸下的水平溢出、攔截 JS 例外、驗證所有本地連結）。以下是 1A2B 這頁被抓出來的問題，以及它們為什麼值得記錄。

1. 一個純粹的算術錯誤：斷點設在錯的地方

右側面板的位置是推導出來的：

$$ \text{left} = \frac{W}{2} + \frac{500}{2} + 20 = \frac{W}{2} + 270 $$

面板本身寬 260px，所以要完整顯示必須滿足：

$$ \frac{W}{2} + 270 + 260 \le W \implies W \ge 1060 $$

但行動版斷點原本寫的是 @media (max-width: 800px)。也就是說，在 801px 到 1060px 之間，版面仍套用桌機的絕對定位，右側面板卻放不進畫面 —— 而且因為 html, body { overflow: hidden } 還生效，使用者既看不到、也捲不到那塊面板。整個歷史紀錄功能在這個寬度區間內憑空消失。

為什麼這種 bug 特別容易漏掉

開發時只會在自己的螢幕（通常 ≥1440px）和手機模擬器（≤430px）兩端測試，801–1060px 剛好是兩者之間的盲區 —— 而它正好對應到「桌機瀏覽器開一半視窗」或「iPad 直向」這些真實常見的情境。修法是把斷點改成 1100px（1060 加上 .shell 的左右 padding 再留一點餘裕）。

2. 視窗高度不足時內容被裁掉

同一個 overflow: hidden 也造成了垂直方向的問題。中央面板內容（統計條 + 85px 數字格 + 兩排 numpad + 按鈕）約需 600px，加上頁首約 700px。在寬 > 1100px 但高 < 700px 的視窗（筆電開著 DevTools、橫向平板）中，translateY(-50%) 會讓內容上下同時溢出，而且捲不動。

補上一個以高度為條件的 media query 解決：

height_query.css
/* 視窗矮的時候允許捲動，並保證絕對定位面板有足夠空間 */
@media (min-width: 1101px) and (max-height: 740px) {
    html, body { overflow: auto; }
    .shell     { height: auto; min-height: 100vh; }
    .game-area { min-height: 620px; }
}

大多數人只寫 max-width 的 media query，但高度也是一個維度，尤其當你用了 100vh 加 overflow: hidden 的滿屏佈局。

3. canvas 拿不到 context，整個遊戲就開不起來

這個問題是在用 jsdom 跑自動化測試時暴露的：測試環境沒有 canvas 實作，getContext('2d') 回傳 null，於是動畫迴圈第一行 ctx.clearRect(...) 就拋出 TypeError。

關鍵在於它拋錯的位置：粒子背景的程式碼寫在整份 script 的最前面，而啟動遊戲的 initGame() 在最後一行。例外一拋，後面全部不執行 —— 玩家看到的是一個完全空白、毫無反應的頁面。一個純裝飾的背景動畫，變成了整個遊戲的單點故障。

defensive_init.js
function initBackground() {
    const canvas = document.getElementById('canvas');
    const ctx = canvas && canvas.getContext ? canvas.getContext('2d') : null;
    if (!ctx) return;      // 不支援就安靜跳過
    // ... 粒子系統 ...
}

// 裝飾性功能失敗，絕對不能拖垮主要功能
try { initBackground(); } catch (err) { /* 背景沒了就算了 */ }

真實世界裡這不只是測試環境的問題：Tor Browser 預設封鎖 canvas 指紋、部分隱私擴充套件也會讓 getContext 回傳 null。裝飾性功能應該可以失敗，而且失敗時要安靜。

4. 鍵盤事件的三個小疏漏

  • 沒有 preventDefault()：Backspace 在某些瀏覽器設定下會觸發「上一頁」導覽。玩到一半整個頁面跳走，進度全失。
  • 沒有過濾修飾鍵：用 Cmd+1 切換瀏覽器分頁時，那個 1 會被遊戲當成輸入吃掉。
  • 標籤與行為不一致：按鈕寫著「清除 (Delete)」，但它只刪一位，而且鍵盤綁的是 Backspace、Delete 鍵根本沒處理。已改成「刪除一位 (Backspace)」並讓兩個鍵都能用。

這三個都不是演算法問題，但它們決定了「這個東西用起來有沒有在細節上出戲」。

XI. 誠實的已知限制

還沒處理、但我知道它們存在的問題：

  • 沒有失敗條件。gameOver 只在 a === 4 時被設為 true。沒有次數上限、沒有投降鈕，所以「勝場紀錄」只增不減，勝率恆為 100%。這是刻意的休閒導向設計，但它讓統計數字失去意義。
  • 統計不持久化。wins 與 best 純在記憶體，重新整理就歸零。加上 localStorage 是十行內的事，目前只是還沒做。
  • 無障礙缺口明顯。數字格是無語意的 <div>，沒有 aria-live 區域播報 A/B 判定結果 —— 而那正是遊戲的核心回饋。螢幕閱讀器使用者實際上無法玩這個遊戲。已用過的數字鍵只加了 class 而沒有真的 disabled，opacity: 0.15 的對比度也遠低於 WCAG 門檻。
  • 沒有 prefers-reduced-motion 保護。無限閃爍的輸入游標動畫違反 WCAG 2.2.2（Pause, Stop, Hide）。
  • CDN 沒有 SRI。confetti 的 <script> 沒有 integrity 屬性。已經加了存在性檢查避免 CDN 掛掉時整頁崩潰，但供應鏈風險仍在。
為什麼把限制寫出來

把「我知道但還沒做」和「我不知道」分開，是我認為技術文件最有價值的部分。前者是待辦清單，後者才是真正的風險。
