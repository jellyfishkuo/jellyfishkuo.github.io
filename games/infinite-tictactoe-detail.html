I. 規則設計：三子上限如何消滅平手

標準井字棋是已被完全解出的和局遊戲：雙方完美下法必定平手，所以成年人玩三局就會膩。這個變體只改一條規則：

核心規則

每位玩家在盤面上最多只能有 3 顆棋子。當你落下第 4 子時，你最早放的那一顆會同時消失。勝負以「落子並移除舊子之後」的盤面判定 —— 也就是說，如果連線需要用到即將消失的那顆棋子，這步不算贏。

這條規則帶來一個結構性的後果：

$$ |Q_X| + |Q_O| \le 3 + 3 = 6 < 9 $$

雙方棋子加起來最多 6 顆，而盤面有 9 格 —— 所以永遠至少有 3 格是空的。盤面不會被填滿，於是「無處可走」這種平手結局在規則上不存在。我用隨機對局實測 200 場，單方棋子數的最大值恆為 3、盤面從未被填滿、每一場都產生了勝者。

但這不等於「賽局論上沒有和局」

這是很容易混淆的一點，值得說清楚：規則上沒有平手結局（不會出現無子可下的僵局），但賽局論上仍然可能是和局 —— 因為雙方都可以永遠互相封鎖，讓對局無限延續下去。這種「無限延續」在賽局論裡就是和局（draw by infinite play）。

換句話說，這個遊戲從「有限、必然結束、必定平手」的標準井字棋，變成了「無限、可能不結束、勝負未知」的賽局。而「勝負未知」正是我想弄清楚的問題。

II. 狀態必須記住「順序」

要分析這個遊戲，第一件事是想清楚「什麼構成一個局面」。標準井字棋的局面就是盤面本身（9 格各為空/X/O）加上輪到誰。但這個變體還必須包含落子的先後順序 —— 因為「下一顆會消失的是哪一個」直接決定了可行的攻擊與防守。

兩個盤面完全相同、但賽局意義完全不同的局面：

        X 的落子順序 (1)(5)(9)          X 的落子順序 (9)(5)(1)
     ┌───┬───┬───┐                 ┌───┬───┬───┐
     │ X │   │   │                 │ X │   │   │  ← 第 1 格最新
     ├───┼───┼───┤                 ├───┼───┼───┤
     │   │ X │   │                 │   │ X │   │
     ├───┼───┼───┤                 ├───┼───┼───┤
     │   │   │ X │  ← 最舊，下一手消失   │   │   │ X │
     └───┴───┴───┘                 └───┴───┴───┘

  X 想連 1-5-9？落子時第 1 格會消失 → 不算贏   X 想連 1-5-9？消失的是第 9 格 → 也不算贏
  但 X 若改連 1-2-3，第 9 格消失不影響 → 可贏   X 若連 7-8-9，第 1 格消失不影響 → 可贏
同一個盤面因為落子順序不同，可行的獲勝路線完全不一樣

所以狀態的定義是：

$$ s = \big(\, Q_X,\ Q_O,\ p \,\big), \qquad Q_i = \text{該玩家棋子的有序佇列（長度} \le 3\text{）} $$

實作上就是兩個 FIFO 佇列。落子與回溯是完全對稱的一對操作 —— 這對後面的搜尋至關重要：

state_transition.js
// 落子：放上新子，超過上限就同時移除最舊的。回傳被移除的位置（無則 -1）
function place(st, pos) {
    const p = st.turn;
    st.cells[pos] = p;
    const q = st.queues[p];
    q.push(pos);
    let removed = -1;
    if (q.length > MAX_PIECES) {
        removed = q.shift();     // 最舊的出隊
        st.cells[removed] = 0;
    }
    st.turn = 3 - p;
    return removed;
}

// 還原一步：把 place 做過的事逐一反轉（供搜尋回溯用）
function unplace(st, pos, removed, player) {
    st.cells[pos] = 0;
    st.queues[player].pop();
    if (removed >= 0) {
        st.queues[player].unshift(removed);   // 放回隊首
        st.cells[removed] = player;
    }
    st.turn = player;
}
先驗證對稱性，再寫搜尋

我做的第一個測試是：隨機亂走幾十步，記下狀態快照，然後 place → unplace，斷言狀態逐位元組完全還原（比對 cells、兩個佇列、輪次）。跑 2,000 輪全過。

這個測試看起來很無聊，但它是所有後續結果的地基：回溯只要有一絲不對稱，深度搜尋算出來的東西全部是垃圾，而且症狀會是「AI 偶爾下很怪的一步」這種幾乎不可能除錯的現象。

III. 完整求解：有環賽局的逆向歸納

既然狀態定義清楚了，一個很自然的問題浮現：這個遊戲的賽局值是什麼？先手有沒有必勝策略？

從初始局面出發做 BFS，枚舉所有可達且尚未產生連線的局面，得到：

$$ |S_{\text{reachable}}| = 116{,}074 $$

十萬個狀態對現代電腦是小規模，可以完整求解。但這裡有個關鍵困難：賽局圖有環（雙方可以走回同一個局面），所以不能用標準的「從終局往回算」的極小極大，那個方法只適用於有向無環圖。

三值的逆向歸納（attractor computation）

正確的做法是三值分類，並用類似 BFS 的方式從終局向外傳播：

  1. 初始化：存在「一步就連線」走法的局面 → 行動方 WIN，距離 1。
  2. 傳播規則 A：若某個子局面是 LOSS（對手行動方必敗），則父局面是 WIN —— 只要有一條路能把對手推進必敗局面就夠了。
  3. 傳播規則 B：若某局面的所有子局面都是 WIN（不管怎麼走都讓對手贏），則它是 LOSS。實作上用一個計數器，每確認一個子節點為 WIN 就減一，歸零時判定必敗。
  4. 剩下的就是和局：傳播結束後仍未被歸類的局面 → DRAW。它們的意義是「雙方都無法逼出勝負，可以無限延續」 —— 這正是有環賽局特有的第三種結果。
retrograde_analysis.js
// unresolved[i] = 還沒被確認為 WIN 的子節點數
while (heap.size) {
    const [d, s] = heap.pop();      // 依距離遞增取出
    if (d !== dist[s]) continue;         // 過期項目

    for (const p of parents[s]) {
        if (value[p] !== DRAW) continue;    // 已定案

        if (value[s] === LOSS) {
            // 🎯 規則 A：能把對手推進必敗局面 → 自己必勝
            value[p] = WIN;
            dist[p] = d + 1;
            heap.push(dist[p], p);
        } else {
            maxChildDist[p] = Math.max(maxChildDist[p], d);
            // 🎯 規則 B：所有走法都讓對手贏 → 自己必敗
            if (--unresolved[p] === 0) {
                value[p] = LOSS;
                dist[p] = maxChildDist[p] + 1;
                heap.push(dist[p], p);
            }
        }
    }
}

IV. 我踩到的坑：明明必勝卻走不出去

算出 WIN / LOSS / DRAW 之後，我寫了一個驗證程式：讓 X 依策略走，窮舉 O 的所有防守，確認 X 每次都贏。策略的第一版看起來理所當然：

broken_strategy.js
// 🐛 第一版：找到任何一個「讓對手必敗」的走法就走
for (const m of emptyCells(st)) {
    place(st, m);
    if (winningLine(st, X)) return m;          // 直接贏
    if (value[idx(st)] === LOSS) return m;   // 對手必敗 → 走這步
    unplace(st, m, ...);
}

驗證結果：123 條路線失敗，最長跑到 41 手還沒收官。

原因：必勝 ≠ 會贏

在有環的賽局裡，「走到一個對手必敗的局面」不足以保證獲勝，因為你可能在一堆必勝局面之間無限繞圈 —— 每一步都維持著理論上的優勢，卻永遠不兌現。這是有限賽局的直覺失效的地方：在 DAG 上，任何往下走的路都會抵達終局；在有環圖上不會。

修法是策略必須讓「距離獲勝的步數」嚴格遞減。這也是為什麼上一節的逆向歸納要用優先佇列依距離遞增處理（Dijkstra 式），而不是普通的 FIFO —— 只有這樣算出的 dist 才具備最小性，可以拿來當策略的下降指標。

錯誤：任選一個必敗子節點

優勢永遠維持，但可能永不收官。123 條路線失敗，41 手仍未結束。

正確：選 dist 最小的必敗子節點

每步距離嚴格 −1，單調遞減保證有限步內抵達終局。98 條路線全數獲勝。

修正後的窮舉驗證結果：

窮舉 O 的所有防守 → 98 條收官路線
最長 13 手（ply），X 落子 7 次
失敗路線：0 條

✅ 先手必勝已驗證
X 依「距離遞減」策略走，O 無論怎麼防都會輸

V. 結果：先手必勝，而且只有「邊」能贏

初始局面的賽局值是 先手必勝，13 手收官。但真正有趣的是九種開局第一手的價值分布：

     ┌─────┬─────┬─────┐
     │  1  │  2  │  3  │        1 角 → 和局
     │  角  │ 邊 ★│  角  │        2 邊 → ★ 必勝（13 手）
     ├─────┼─────┼─────┤        3 角 → 和局
     │  4  │  5  │  6  │        4 邊 → ★ 必勝（13 手）
     │ 邊 ★│  中  │ 邊 ★│        5 中 → 和局
     ├─────┼─────┼─────┤        6 邊 → ★ 必勝（13 手）
     │  7  │  8  │  9  │        7 角 → 和局
     │  角  │ 邊 ★│  角  │        8 邊 → ★ 必勝（13 手）
     └─────┴─────┴─────┘        9 角 → 和局
只有四個「邊」格是必勝開局，中央與四角都是和局
這和標準井字棋完全相反

在標準井字棋裡，中央是最強的第一手（它參與四條連線，角落三條，邊只有兩條）。但在三子上限的變體裡，中央變成了和局，只有邊格必勝。

直覺上的解釋是：中央參與的連線最多，代表它同時也是最容易被利用的位置 —— 而在這個變體裡，你的棋子會不斷消失，佔住一個「潛力大但需要長期維持」的格子反而是負擔。邊格參與的連線少，卻更容易在三顆棋子的短生命週期內兌現成實際的連線。這是一條規則改動就翻轉了整個開局理論。

對遊戲設計的實際影響

先手有必勝策略，這對一個休閒遊戲來說是個真實的平衡問題。我在實作上的處理是：提供「先手／後手」選項，讓玩家可以選擇執 X（較有利）或執 O（挑戰）。既然數學已經告訴我先手優勢是結構性的、無法靠規則微調消除，那就把它變成一個明確的難度選項，而不是假裝它不存在。

VI. AI：negamax + Alpha-Beta，以及一個變體特有的評估難題

遊戲內的 AI 不使用上面那張 116,074 筆的解答表 —— 那樣就變成查表機器人，而且無法調整難度。它是一個標準的深度受限 negamax 搜尋，配 alpha-beta 剪枝：

negamax.js
function negamax(st, depth, alpha, beta) {
    let best = -Infinity, bestMove = -1;

    for (const m of emptyCells(st)) {
        const player = st.turn;
        const removed = place(st, m);
        let score;

        if (winningLine(st, player)) {
            score = WIN_SCORE + depth;   // 剩餘深度越多 = 越早贏 = 越好
        } else if (depth <= 1) {
            score = -evaluate(st);      // turn 已換人，取負轉回 player 視角
        } else {
            score = -negamax(st, depth - 1, -beta, -alpha).score;
        }
        unplace(st, m, removed, player);

        if (score > best) { best = score; bestMove = m; }
        if (score > alpha) alpha = score;
        if (alpha >= beta) break;              // 剪枝
    }
    return { score: best, move: bestMove };
}

評估函式必須認得「即將消失的棋子」

這是本變體與標準井字棋最大的實作差異。一般井字棋的評估函式看到「某條線上我有 2 顆、第 3 格是空的」就判定為強烈威脅。但在這裡，如果那 2 顆之中包含即將消失的那一顆，這個威脅是假的 —— 你落下第 3 子的同時，最舊的那顆就消失了，連線不成立。

evaluate.js
function lineScore(st, p) {
    // 該玩家下一手會消失的棋子位置（未滿 3 子則為 -1）
    const doomed = doomedCell(st, p);
    let s = 0;

    for (const line of LINES) {
        let mine = 0, theirs = 0, doomedInLine = false;
        for (const idx of line) {
            if (st.cells[idx] === p) {
                mine++;
                if (idx === doomed) doomedInLine = true;
            } else if (st.cells[idx] === 3 - p) theirs++;
        }
        if (theirs > 0) continue;   // 被封死的線沒有價值

        // 🎯 用到即將消失的棋子，威脅大打折（12 → 3）
        if (mine === 2) s += doomedInLine ? 3 : 12;
        else if (mine === 1) s += 1;
    }
    return s + positionalBonus;
}

沒有這個折價，AI 會不斷追逐永遠兌現不了的假威脅，同時漏掉對手真正的攻勢。

VII. 難度階梯與實測強度

難度就是搜尋深度加上一點刻意的失誤率：

難度 搜尋深度 隨機亂下機率 空盤思考時間
簡單 2 45 % < 1 ms
普通 5 12 % < 1 ms
困難 12 0 % 約 40 ms

對戰實測（每組數十至上百場）：

  • 困難 vs 隨機亂下：100 : 0
  • 困難（先手）vs 普通：40 : 0
  • 困難 vs 困難：先手方 20 : 0 全勝 —— 這個現象在我求解之前就出現了，事後回頭看，它正是「先手必勝」的實證訊號。
最漂亮的驗證：AI 自己找到了理論最佳開局

我拿求解結果去檢查 AI 的第一手選擇（各跑 200 次）：

困難（深度 12）   邊 100%                    ← 完全命中理論必勝手
普通（深度 5）    邊 92%   角 5%   中 4%
簡單（深度 2）    中 62%   角 20%  邊 19%    ← 落入「中央最強」的錯誤直覺

深度 12 的啟發式搜尋在不知道解答表的情況下，100% 選中了唯一的必勝開局；而深度 2 的淺層搜尋則落入了標準井字棋的直覺陷阱，62% 選中央 —— 那在這個變體裡只是和局。啟發式評估的品質，就這樣被賽局論的答案量化了出來。

VIII. 前端：讓「即將消失」變得看得見

這個變體最大的體驗風險是：玩家會忘記自己的棋子要消失，然後在關鍵時刻愣住。UI 上用了三層提示：

  • 虛線框 + 呼吸閃爍：輪到你時，下一手會被移除的那顆棋子套上 .doomed，虛線邊框加 1.4 秒的 opacity 動畫。
  • 狀態列文字：「落子後第 N 格會消失」，把視覺提示翻譯成明確的文字。
  • 步數紀錄：每一步都記下「X → 第 7 格（第 1 格消失）」，讓玩家可以回溯理解棋子的生命週期。

另外一個細節：只提示「輪到的那一方」即將消失的棋子。同時顯示雙方的話畫面太吵，而且對手的消失預告在你思考時是干擾而非資訊。

IX. 工程反省：手機版整個重做

這頁上線後我用裝置模擬做了一輪檢查，發現手機版雖然沒有排版溢出，但體驗上有幾個實質問題。值得記錄的是：這些問題用桌機瀏覽器縮視窗測不出來。

一個誤導我很久的測試假象

我一開始用 headless Chrome 加 --window-size=390,844 截圖，看到棋盤第 3、6、9 格被切掉，以為是嚴重的溢出 bug。實際上那是假象 —— macOS 上的 headless Chrome 有 500px 的最小視窗限制，所以它是「用 500px 排版再裁切成 390px」。

正確的做法是用 CDP 的裝置模擬（Emulation.setDeviceMetricsOverride），讓 meta viewport 真正生效。換過去之後才量到真實數據。工具的限制會偽裝成程式的 bug，這個教訓比那個 bug 本身有價值。

}

X. 裝飾性功能不該拖垮主功能

用 jsdom 寫自動化測試時，整個遊戲完全開不起來 —— 因為測試環境沒有 canvas 實作，getContext('2d') 回傳 null，粒子動畫的第一行就拋 TypeError，而它排在遊戲初始化之前。

這不只是測試環境的問題：Tor Browser 預設封鎖 canvas 指紋，部分隱私擴充套件也會讓 getContext 回傳 null。修法是把背景動畫包成函式、加上能力檢測，並用 try/catch 隔離：

isolation.js
function initBackground() {
    const ctx = canvas && canvas.getContext ? canvas.getContext('2d') : null;
    if (!ctx) return;    // 環境不支援就安靜跳過
    // ...
}
try { initBackground(); } catch (err) { /* 背景動畫失敗就算了，遊戲照常 */ }

同樣的 bug 也存在於1A2B 那頁（同源的粒子背景程式碼），一併修掉了。一個純裝飾的背景動畫，不該成為整個應用的單點故障。

XI. 誠實的已知限制

  • AI 不是完美的。它是深度 12 的啟發式搜尋，不查解答表。深度 12 在中局可能看不到更深的必勝路線，所以理論上一個完美的人類玩家（尤其執先手走邊格）可以贏過困難難度。我刻意不把 116,074 筆解答表塞進頁面 —— 那會讓遊戲變成不可能贏的查表機器人，而且檔案大小會爆掉。
  • 手機橫向仍需小幅捲動。844×390 時棋盤下緣超出視窗約 70px。要完全塞進去得把棋盤縮到 240px 以下，反而更難點，所以保留捲動。
  • 沒有棋譜記錄或悔棋。步數紀錄只是文字，無法回溯到任意一步。實作悔棋需要保存狀態堆疊（含兩個佇列），不難但還沒做。
  • 無障礙仍不完整。棋格是 <button> 且有 aria-label、狀態列是 role="status" 的 live region，這部分還可以；但「即將消失」這個關鍵資訊主要靠虛線與閃爍傳達，螢幕閱讀器使用者只能靠狀態列的文字。
  • 先手優勢無法消除。已由求解證明是結構性的。目前用「可選先後手」處理，但若要真正平衡，得改規則（例如後手第一手可以放兩子，或改成 4 子上限）—— 那就是另一個遊戲了。
